## 1. 增量目标与范围

### 1.1 产品目标（正交三条）

1. **让需求能启动研发**：研发负责人可从一条需求发起研发任务并明确绑定该需求，使"需求 → 研发"在平台内可追溯；一条需求允许存在多个研发任务（推翻"一需求一任务"）。
2. **让研发进度可见可控**：每个任务自动拆出前端/后端两个子任务，二者各走同一套 8 态状态机；负责人通过看板/列表查看、用手动按钮推进状态，作为后续人工审核与交付编排的事实基线。
3. **零迁移、零破界**：在 V1.0/V1.1 已上线能力上做最小增量，不改菜单形态、不改权限模型（尤其不新增写点）、不触碰需求中心以外的 3 个菜单。

### 1.2 本次范围边界（严格遵守用户 6 项拍板）

| 菜单 | 本次交付 | 边界说明 |
| --- | --- | --- |
| 01 需求中心 | ❌ **不动** | 含 V1.1 项目关联与图片能力，本次一律不改 |
| 02 AI研发中心 | ✅ **仅此菜单升级为做实页** | 研发任务的创建/列表/详情/状态流转；权限仍用 `rdc.dev.read` |
| 03 人工审核中心 / 04 需求交付中心 | ❌ **不动** | 保持真实空态骨架页现状 |
| 菜单/权限形态 | **保持不变** | 仍为 team 级平台菜单；不新增权限点、不新增写点、不引入项目角色 |

> **本版范围 = 管理平台编排层**：状态推进是纯平台编排动作（人工点按钮改状态），**不接 Agent、不触发任何真实研发/Git/测试动作**。5 个子功能（Git 工作区、开发环境、数据库、Agent 调度、自动测试）在页面内仅以**文字说明块**列出并标注"后续迭代开放"，**禁止放置可点击的"执行/连接/创建"按钮**（反占位约束，呼应 AGENTS.md §3/§6）。

### 1.3 五项用户决策落地口径（不可违背）

1. **只做编排层**：研发任务 = 平台里的进度编排对象，不是执行器。
2. **一对多**：一条需求可建多个研发任务；任务**必须**绑定需求（`requirement_id` 为准，`reqKey` 用于展示/筛选，见 §4.1）。
3. **共享 8 态状态机**：前后端子任务各走一套 `PENDING → AI_RUNNING → AI_COMPLETED → REVIEWING → WAITING_COMMIT → COMMITTED → VALIDATED → COMPLETED`，另有 `SKIPPED`（无需开发）。
4. **不新增写权限点**：菜单与页面内所有操作（创建任务、推进状态、标 SKIPPED）**统一用 `rdc.dev.read`** 守；前端不再加任何写点判断。
5. **创建即拆两个子任务**：前端 + 后端，各为 `PENDING`；用户可在详情把不需开发的子任务标 `SKIPPED`。
6. **手动按钮推进**：只能前进到下一态（终态不可用），不能跳级/回退；`SKIPPED` 是唯一的非线性设定且不可恢复（见 §8 待确认 Q2）。

## 2. 用户故事

1. **作为研发负责人**，我希望从一条需求发起研发任务并自动绑定该需求，以便每个任务都有明确来源、后续可反向追溯到需求。
2. **作为研发负责人**，我希望同一条需求能建多个研发任务（如"前端重构"与"接口联调"分开推进），以便按工作包组织研发而不受"一需求一任务"限制。
3. **作为研发负责人**，我希望新建任务时系统自动拆出前端/后端两个子任务（均待开发），以便我无需手工初始化就能看到研发的两条主线。
4. **作为研发负责人**，我希望在任务详情里点按钮把子任务推到下一状态，以便用统一看板反映进度；且推进只是平台编排，不会误触发真实研发动作。
5. **作为研发负责人**，我希望把不需开发的子任务（如纯后端需求的前端部分）标为 `SKIPPED`，以便看板只聚焦真正要做的部分。
6. **作为研发负责人**，我希望按需求（`reqKey`）或状态筛选研发任务，以便在任务多时快速收敛到关心的一批。
7. **作为未授权成员 / solo 模式用户**，我希望看不到 `/rdc/dev`、直连也被拦截；作为公司管理员，我希望看不到其他公司的需求与任务——以便数据边界清晰、不越权。

## 4. 数据模型（PRD 层，非 DDL）

> 仅定义实体、字段语义与约束；表名/列类型/索引/外键/幂等 DDL 由架构师在 `schema.sql` 落实。风格沿用 `snake_case`、UUID 主键、`created_at`、`rdc_` 前缀、**team 专属分区**（沿用 V1.0 决策 D3：`RequireTeamMode` 是模式边界，不为用不到的 solo 造表）。

### 4.1 研发任务实体 `rdc_dev_task`（建议名）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `id` | 主键 | UUID，服务端生成 |
| `requirement_id` | **绑定需求**（一对多的"多"侧外键） | 指向 `team.rdc_requirements.id`，**必填**；一条需求可对应多条本表记录；跨租户需求被拒 |
| `req_key` | 需求编号（展示/筛选投影） | **建议不冗余存列**：由关联 `rdc_requirements.req_key` 投影得到；若架构师为筛选性能需要冗余，须与需求侧同步且不可变（见 §8 Q1） |
| `title` | 任务名称（用户填写） | 必填，建议 ≤ 100 字；同一需求下允许多条同名任务，不设唯一约束 |
| `creator_user_id` | 创建人 | 裸 TEXT（沿用 `projects/builds` 惯例，不加 users 外键）；展示名 JOIN 投影，不冗余 |
| `tenant_id` | 公司隔离 | 从 `scope` 取，请求体不含 `tenantId`/`creatorUserId` |
| `created_at` | 创建时间 | 服务端 |
| `project_id` / `projectName` | 项目名（可选列） | **不存列**：经 `requirement_id → rdc_requirements.project_id → team.projects.name` 投影；存量需求无归属时显示"未归属项目" |

**任务整体状态**：本 PRD **建议不新增 `status` 列**，由两个子任务聚合推导（见 §4.3）。若架构师选择落列，需与 §4.3 聚合口径保持一致（见 §8 Q1）。

### 4.2 子任务实体 `rdc_dev_subtask`（建议名）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `id` | 主键 | UUID，服务端生成 |
| `task_id` | 所属研发任务 | 指向 `rdc_dev_task.id`，一对多；任务删除时级联（若本版不做删除则无级联路径） |
| `kind` | 子任务类型 | 枚举 `frontend`｜`backend`；一个任务固定各一条，创建时成对生成 |
| `status` | 子任务状态 | 9 个枚举值（8 态 + `SKIPPED`），默认 `PENDING`；枚举唯一来源放 `api/openapi.yaml`，DDL 不加 CHECK（沿用惯例） |
| `created_at` | 创建时间 | 服务端 |
| `updated_at` | 状态最后变更时间（建议） | 便于详情展示"最近推进"，非必需 |

### 4.3 "一条需求多个任务"如何体现

- 多个 `rdc_dev_task` 记录共享同一个 `requirement_id`；列表按 `reqKey` 筛选时，经需求 JOIN 过滤（`reqKey` 不冗余时）或直接按 `req_key` 列过滤（冗余时）。
- **状态筛选口径（建议）**：以"任务整体状态"筛选。任务整体状态由两条子任务聚合：
  - `SKIPPED` 子任务视为"已通过、不参与比较"；
  - 其余子任务中取**进度最靠前**（状态序号最小）的那条状态作为任务整体状态；
  - 两条都 `COMPLETED` 或 `SKIPPED` 时，任务视为**完成**。
  - 该聚合为纯展示/筛选逻辑；若采用落列方案，则由 service 在每次状态变更后重算并写回（见 §8 Q1）。
- 需求侧无需改动任何字段；需求删除路径本就不存在（详情只读），FK 无需 `ON DELETE CASCADE`。

## 5. 状态机定义

> 状态标识以下用大写名讨论；实际枚举值大小写/命名（如 `pending` / `ai_running`）由 `api/openapi.yaml` 唯一确定，架构师定。中文标签在 `utils/format.ts` 镜像。

### 5.1 八态 + SKIPPED

| 序 | 状态 | 中文标签 | 说明 |
| --- | --- | --- | --- |
| 0 | `PENDING` | 待开发 | 子任务创建默认态 |
| 1 | `AI_RUNNING` | AI 执行中 | 编排占位态（本版由手动推进触发，不接 Agent） |
| 2 | `AI_COMPLETED` | AI 已完成 | 编排占位态 |
| 3 | `REVIEWING` | 审核中 | 编排占位态 |
| 4 | `WAITING_COMMIT` | 待提交 | 编排占位态 |
| 5 | `COMMITTED` | 已提交 | 编排占位态 |
| 6 | `VALIDATED` | 已验证 | 编排占位态 |
| 7 | `COMPLETED` | 已完成 | **终态**，推进按钮不可用 |
| — | `SKIPPED` | 已跳过（无需开发） | **终态**，不可恢复，推进按钮不可用 |

### 5.2 合法转换表（只能前进到下一态）

| 当前状态 | 「推进到下一状态」按钮 | 目标状态 |
| --- | --- | --- |
| `PENDING` | 可用 | `AI_RUNNING` |
| `AI_RUNNING` | 可用 | `AI_COMPLETED` |
| `AI_COMPLETED` | 可用 | `REVIEWING` |
| `REVIEWING` | 可用 | `WAITING_COMMIT` |
| `WAITING_COMMIT` | 可用 | `COMMITTED` |
| `COMMITTED` | 可用 | `VALIDATED` |
| `VALIDATED` | 可用 | `COMPLETED` |
| `COMPLETED` | **不可用**（终态） | — |
| `SKIPPED` | **不可用**（终态） | — |

**约束**
- 禁止跳级（一次只进一态）、禁止回退；服务端必须校验"（当前态，目标态）"在合法集合内，非法返回 400，不能只靠前端禁用按钮。
- `SKIPPED` 是唯一非线性转移：可从 `PENDING` 或**任意未完成态**（即序 0–6）设置；不可从 `COMPLETED` 或 `SKIPPED` 设置；设置后不可恢复（见 §8 Q2）。
- 终态下"推进"与"标为跳过"按钮均不可用（跳过按钮在已跳过时隐藏或禁用）。
- 本版所有推进均为**平台编排**：service 只改 `status`（与 `updated_at`），**不调用任何 Agent / Git / 测试执行器**。

## 6. 页面设计

> 沿用现有规范：`DataTable` 服务端分页、`page` 进 URL、`States` 三态、`Controls.Segmented` 做筛选/切换、详情优先抽屉、UI 组件来自 `@seakoi/console-kit` 根入口、主色 `#0369a1`。所有操作只依赖 `rdc.dev.read`，**前端不再加写点判断**（`me` 仍在 `PermissionGate`/菜单层按读点控制，未授权不可达）。

### 6.1 主页面 `/rdc/dev`（研发任务看板/列表）

- 标题「AI研发中心」+ 简短说明（"从需求发起研发任务，编排前后端研发进度"）。
- 主操作「新建研发任务」：有 `rdc.dev.read` 即可见可用（本版不按写点隐藏）。
- 列表列：**任务名称**（详情入口）/ **关联需求 `reqKey`** / **项目名**（可选，经需求投影，空值显示"未归属项目"）/ **子任务状态**（两个标签：`前端: <状态>`、`后端: <状态>`）/ **创建人** / **创建时间**。
- 筛选：**按需求 `reqKey`** + **按任务状态**（口径见 §4.3），可叠加；服务端分页（页码进 URL）；空列表用空态卡片、不挂分页条。
- 点击任务名称（或行）打开详情抽屉。

### 6.2 新建任务表单 `/rdc/dev/new`

- **来源需求**：下拉单选，只列本公司需求（复用需求列表接口的全量 `pageSize=0` 或专用下拉接口，显示 `reqKey + title`）；未选不可提交；后端复校需求存在且属当前 `tenant`，越界返回 400/404。
- **任务名称**：必填，≤100 字。
- 提交成功后：创建任务 + 自动拆 `frontend`/`backend` 两条 `PENDING` 子任务；回列表并提示任务已创建（可自动打开详情，产品建议）。
- 不提供"自行选择子任务类型/初始状态"等入口——固定成对、固定初始态，避免多余配置。

### 6.3 任务详情抽屉（列表点击任务名打开）

- **绑定需求信息**：`reqKey`、`title`、项目名（投影）、创建人/时间（只读）。
- **两个子任务卡片**（`frontend` / `backend` 各一）：
  - 状态标签（中文）；
  - 「推进到下一状态」按钮：按 §5.2 显示目标态（如"推进到 AI 执行中"），终态禁用/隐藏；
  - 「标为跳过」按钮：未完成态可用，点击弹二次确认；`COMPLETED`/`SKIPPED` 不可用；
  - 最近推进时间（若有 `updated_at`）。
- **5 个占位子功能说明块**：Git 工作区 / 开发环境 / 数据库 / Agent 调度 / 自动测试，逐项标注"后续迭代开放"，**纯文字，无按钮、无链接、无请求**。
- 本版不提供任务编辑/删除/子任务负责人入口（避免假操作）。

### 6.4 无假按钮约束（重申）

- 5 个子功能在本版**只做说明**，不注册路由、不建 handler、不进 `openapi.yaml`（否则契约一致性测试失败）；详情页不得出现任何"执行/连接/创建工作区/调度 Agent/运行测试"的可点控件。
- 状态推进按钮是真实可用的（改平台状态），但它只做编排，UI 文案避免暗示"已触发真实研发"（如用"推进状态"而非"开始执行"）。

## 7. 权限与隔离

### 7.1 权限点不变（重申用户决策 4）

- `/rdc/dev` 仍由 **`rdc.dev.read` 单点守护**：菜单可见性、路由守卫、列表/详情/新建/状态推进/SKIPPED 全部用它。
- **不新增 `rdc.dev.write`**；前端页面内任何按钮都不做写点判断（这是有意偏离 `build.read/write`、`rdc.requirement.read/write` 的读写分离惯例，以用户拍板为准）。
- 路由仍是 team 级平台专区：`RequireAuth → InjectScope → RequireTeamMode → RequirePermission(rdc.dev.read)`；`TeamModeGate` 在 `PermissionGate` 外层先挡模式（沿用 V1.0 决策 D7）。
- 前端写入口不再用 `can(me, ...write...)`；但 `me` 为 null 时按无权限处理（由上层 Gate 统一承担）。

### 7.2 数据隔离

- **平台级 team 专区**：solo（含 solo 超管）侧栏不出现、直连 `/rdc/dev` 显示"仅团队模式可用"且不发请求；后端 `RequireTeamMode` 是真正边界（solo → 403）。
- **租户隔离**：任务表带 `tenant_id`；列表/详情/状态推进查询统一先经 `repository.ScopeFilter(alias, scope)` 再叠加业务条件；跨公司任务/详情按 **404** 处理，不泄漏存在性。
- **需求来源隔离**：新建时的需求下拉只列本公司需求；后端**必须**复校所选 `requirement_id` 存在且属当前 `tenant`（超管 `scope.All` 沿用现有平台级可见范围约定），越界拒绝写入。
- 归属字段 `tenant_id` / `creator_user_id` 只从 `scope` / 身份取；请求体不接受 `tenantId` / `creatorUserId`（未知字段按现有严格解码规则拒绝）。

## 8. 待确认问题（请 lead 转用户决策）

> 以下为产品侧认为需明确之处；未拍板前架构师可按本节"建议"推进，但不视为用户已决策。

1. **Q1｜任务整体状态是否落列**：PRD 建议**不新增 `status` 列**，由两条子任务按 §4.3 聚合（取进度最靠前者，`SKIPPED` 不参与；两条终态视为完成）。请确认该聚合口径，尤其"两条都 `SKIPPED`"时任务显示为 `SKIPPED` 还是 `COMPLETED（无需开发）`。若选择落列，请确认由 service 在每次状态变更后重算写回。
2. **Q2｜`SKIPPED` 不可恢复 + 误点防护**：决策为"不可恢复"。产品建议 UI 上"标为跳过"加二次确认（写清影响面，符合 AGENTS.md §6）。请确认"完全不可恢复"是否为最终口径；若用户在意误点，是否接受"仅限本次详情打开期间可撤销（不改持久化状态机的不可逆性）"——此项会触及恢复语义，需用户明确。
3. **Q3｜审计留痕**：研发任务的**创建**是否写入 `team.audit_logs`（对齐需求创建）？**状态推进 / `SKIPPED` 标记**是否也写（便于追溯"谁在何时把哪条子任务推到何态"）？产品建议：创建必写；状态变更也写（detail 记 `taskId`/`kind`/`from`/`to`），失败只记日志不回滚。请确认审计范围。
4. **Q4｜任务生命周期能力**：本版产品建议任务创建后除状态操作外**只读**（不做编辑/重命名/删除），以避免假操作；且因需求中心本就无删除路径，FK 不设级联。请确认本版是否确实不需要任务删除/编辑入口。
5. **Q5｜需求绑定的键**：建议以 `requirement_id`（UUID FK，稳定）为绑定真相，`reqKey` 仅作展示/筛选（默认不冗余存列）；若架构师为筛选性能需要冗余 `req_key` 列，须保证与需求侧不可变值一致。此项偏技术实现，交由架构师定夺，不阻塞本 PRD。

> 除上述外无阻塞性问题。5 个占位子功能保持文字说明、不接执行器、不写假按钮，为本版硬约束。
