## 1. 增量目标与范围

### 1.1 本版定位（最重要，先读）

> **本版 = 定义「Agent 产出 → 交互层」的数据契约与产品交互规范（纯设计），不写实现代码、不依赖未就绪的 Agent 执行器。**

- 四步交互体系（1–4）**全部纳入本版**，但"全做"的口径是：**四步的数据契约、对象模型、状态/决策语义、产品规则与 UI 交互规范全部定义清楚**，让隔离执行器就绪后 UI / 后端**直接对接、不返工**。
- **不承诺、不实现 Agent 执行本身**；**不写任何假数据 / 假 diff / 假按钮 / TODO**（反占位，呼应 AGENTS.md §3/§6）。本 PRD 中出现的所有结构示例均为"契约形状说明"，不是可在页面上产生的模拟数据。

### 1.2 关键前提（安全阻塞，写进边界）

| 前提 | 事实 | 对本版的影响 |
| --- | --- | --- |
| 02 AI研发中心现状 | **纯管理平台编排层**：8 态 + `rejected` + `resubmit`（`contract.DevAdvance` / `x-rdc-dev-transitions`），手动推进状态；`ai_running` / `ai_completed` 只是**状态标签**，背后无 Agent 执行、无 diff 产出 | 四步交互的"产出源"目前不存在；本版只定义"当有真实产出时，交互层怎么接" |
| Agent 执行 / Git 直读 | 用户明确要求"Agent 必须完整隔离后才启用"；Windows 测试环境缺失、macOS 隔离资源未就绪，Git 直读处于**安全阻塞**（详见 `rdc-delivery-git-isolation-design.md` §6/§7） | **数据源必须等 Agent 真产出**（用户拍板 1）；执行器与隔离就绪前，四步交互只有契约、没有运行时 |
| 审核中心现状 | 已有"审核通过 / 驳回 / 提交确认"流程与 `team.rdc_review_record` 留痕（关联键 `task_id` / `subtask_id`，动作 `approve`/`reject`/`commit`/`resubmit`）；前端 `ReviewDetailDrawer` 把前端 Diff / 后端 Diff / 编辑器打开列为"后续开放"占位 | 本方案的 Diff 审查 / 检查点 / 分级审批**必须与此划清边界**（见 §7 产品建议：升级而非新建） |

### 1.3 三项用户拍板（不可违背）

1. **数据源 = 等 Agent 真产出**：交互挂在真实 Agent 产出的 diff 上，不用人工录入的模拟数据。执行器未就绪 ⇒ 只定义契约，不做演示数据。
2. **本版范围 = 全做 1–4**：四步交互体系一次定义到位（口径见 §1.1：到契约/规范层）。
3. **右栏实时预览 = 应用后的文件内容**：右栏展示"接受当前 hunk 之后"的**文件完整内容**，由**纯前端计算**得到，**不改真实文件**；支持**多文件 tab**。**不是**只预览 diff 高亮，**也不**渲染运行效果。

### 1.4 产品目标（正交三条）

1. **受控**：把 AI 产出拆成可逐 hunk 审查、可局部取舍的工程对象，用户对每一行改动有决定权（对应第 1 步）。
2. **对齐**：在执行前把意图对齐（结构化问卷 + 可确认任务列表），减少"产出后推翻重来"（对应第 2 步）。
3. **敢用且可持续**：每次 AI 动作可精确回滚、按风险自动调节人工介入强度，既给心理保障，又避免高频低风险操作造成审批疲劳（对应第 3、4 步）。

### 1.5 范围边界

- **本次交付物**：一份数据契约与交互规范（本文）+ 架构师据此的接口契约设计。**不含**、**不实现**：Agent 调度、真实 diff 生成、文件写入、测试执行、Git 操作。
- **已实现基线**：01 需求中心、02 研发任务编排、03 人工审核中心、04 需求交付中心，**本版均不改其既有能力与状态机**；本方案只在契约层为它们预留关联键与升级点。
- **菜单 / 权限**：不新增菜单、不新增写点（建议沿用 `rdc.dev.read` / `rdc.review.read` 现状，见 §7）。solo 不可见、不可达（沿用团队专区）。
- **反占位**：隔离执行器未就绪期间，**不**在页面上放"生成 / 接受 / 回滚"等可点但没有真实数据源的按钮；相关能力在契约定稿、执行器就绪后再落 UI。

## 2. 用户故事

1. **作为研发负责人**，我希望逐 hunk 接受或拒绝 AI 的改动，并在右栏实时看到"接受后文件会变成什么样"，以便我对每一行代码保持控制，而不是被迫整体接受一个黑盒。（第 1 步 · Diff 审查）
2. **作为研发负责人**，我希望在 AI 生成之前先回答结构化问卷并确认任务列表，确认前不开始生成，以便把需求对齐前置、减少返工。（第 2 步 · 计划确认）
3. **作为研发负责人**，我希望每一次 AI 动作都有可回滚标识，能按单 hunk / 单文件 / 整个检查点回退，以便我"敢让 AI 动手"——出了问题能精确撤销。（第 3 步 · 检查点回滚）
4. **作为研发负责人**，我希望格式化、加注释这类低风险改动免审批、直接通过，以便高频小改动不被审批流拖慢、不产生审批疲劳。（第 4 步 · 分级审批 · 低风险免审）
5. **作为研发负责人 / 安全负责人**，我希望删文件、改配置、装依赖等高风险改动触发强制人工审批，且风险等级由操作类型自动判定，以便关键变更绝不悄悄溜过。（第 4 步 · 分级审批 · 高风险强审批）
6. **作为公司管理员**，我希望这些交互数据与研发任务 / 子任务绑定、按公司隔离，且不引入第二套审核历史，以便追溯"谁在何时接受了哪些 hunk"，又不破坏既有数据边界。（权限与隔离）

## 4. 数据模型（PRD 层，非 DDL）

> 仅定义实体、字段语义与产品约束；表名/列类型/索引/外键/幂等 DDL 由架构师在 `schema.sql` 落实。沿用 `snake_case`、UUID 主键、`created_at`、`rdc_` 前缀、**team 专属分区**（沿用研发中心"不为 solo 造表"决策，写在 `FOREACH` 循环之外）。**枚举唯一来源放 `api/openapi.yaml`，DDL 不加 CHECK。**

### 4.1 Diff 审查对象 `rdc_diff_review`（建议名）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `id` | 主键 | UUID，服务端生成 |
| `task_id` / `subtask_id` | **关联键**：挂在哪个研发任务 / 子任务下 | 指向 `team.rdc_dev_task(id)` / `team.rdc_dev_subtask(id)`；必填；与审核记录同键，便于串起审核历史 |
| `checkpoint_id` | 关联检查点（§4.3） | 指向本次 AI 动作的检查点；一次 AI 动作 = 一份 diff 审查 + 一个检查点 |
| `source` | 数据来源标识 | **必填且只能是 `agent_executor`**（真实 Agent 产出）；本版禁止 `manual` 之类模拟来源（拍板 1）。执行器未就绪时该对象**不产生运行时数据** |
| `files[]` | 文件级 diff 列表 | 见下 `FileDiff` |
| `submit_status` | 审查提交状态 | 枚举 `pending` / `submitted`；当且仅当所有 hunk 的 `decision != pending` 时允许提交 |
| `tenant_id` / `created_at` | 公司隔离 / 创建时间 | 从 `scope` 取；服务端 |

**`FileDiff`**

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `file_path` | 文件路径（仓库相对路径） | 唯一标识一个文件 tab；经执行器/脱敏后给出，前端不接收绝对路径 |
| `file_status` | 变更类型 | 枚举 `added` / `modified` / `deleted` / `renamed` |
| `old_path` | 重命名前路径 | 仅 `renamed` 时有值 |
| `hunks[]` | 该文件的 hunk 列表 | 见下 `Hunk` |

**`Hunk`**

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `hunk_id` | hunk 唯一标识 | UUID 或执行器给出的稳定 id，审查域内唯一 |
| `old_start` / `old_lines` / `new_start` / `new_lines` | **行号**（起始行 + 行数） | 用于定位与右栏"应用后内容"计算；口径统一（建议 1-based，交架构师与执行器对齐，见 §8 Q1） |
| `old_content` / `new_content` | **旧内容 / 新内容**（逐行文本数组） | 真实来自 Agent 产出的 diff；本版不生成示例内容 |
| `context_before` / `context_after` | **上下文**（可选，或内嵌于内容） | 供中栏行级 diff 展示；是否独立字段交架构师 |
| `decision` | **每个 hunk 的接受-拒绝状态** | **三态** `pending` / `accepted` / `rejected`，默认 `pending`。三态是"全部处理完才提交"门禁的基础（二态无法区分未处理） |
| `risk_label` | **风险标签 / 操作类型** | 关联 §4.4 分级审批：如 `delete_file` / `config_change` / `dependency_change` / `schema_migration` / `code_edit` / `format` / `comment` / `doc`；由执行器 diff 元数据给出或按 §5.4 规则判定 |

### 4.2 计划确认对象 `rdc_plan_confirmation`（建议名）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `id` | 主键 | UUID，服务端生成 |
| `task_id` / `subtask_id` | 关联键 | 同 §4.1，挂在研发任务 / 子任务下 |
| `questionnaire[]` | **结构化问卷** | 见下 `Question`；执行器/规划阶段产出 |
| `plan_tasks[]` | **可确认任务列表** | 见下 `PlanTask` |
| `gate_status` | 门禁状态 | 枚举 `blocked` / `confirmed`；初始 `blocked`；**所有必答问题已答 + 所有任务已确认** → `confirmed`，才允许进入执行（§5.2） |
| `confirmed_by` / `confirmed_at` | 确认人 / 时间 | 裸 TEXT 用户 id + 服务端时间 |
| `tenant_id` / `created_at` | 公司隔离 / 时间 | 从 `scope` 取 |

**`Question`**：`question_id` / `prompt`（题干）/ `type`（`single`｜`multiple`｜`text`）/ `required`（是否必答）/ `options[]`（`option_id` + `label`）/ `answer`（答案，对应选项 id 或文本；必答题未答则门禁不放行）。

**`PlanTask`**：`step_id` / `title` / `description`（这一步 AI 要做什么）/ `confirmed`（是否已确认，默认 false）/ 可选 `estimated_risk`（预标注风险，供 §5.4 参考）。

### 4.3 检查点对象 `rdc_checkpoint`（建议名）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `id` | 主键 | UUID，服务端生成 |
| `task_id` / `subtask_id` | 关联键 | 同 §4.1 |
| `ai_action` | **"一次 AI 动作"的标识/描述** | 见 §5.3.1 定义；一个已确认的计划步骤的一次执行 = 一个检查点 |
| `files[]` | **文件 before/after 快照** | 见下 `FileSnapshot` |
| `rollback_token` | **可回滚标识** | 服务端生成的幂等令牌；回滚必须携带它，防重复/越权回滚（见 §5.3.3） |
| `status` | 检查点状态 | 枚举 `active` / `rolled_back` / `partially_rolled_back` |
| `created_by` / `created_at` | 触发人 / 时间 | 裸 TEXT + 服务端时间 |
| `tenant_id` | 公司隔离 | 从 `scope` 取 |

**`FileSnapshot`**：`file_path` / `before_content`（动作前完整内容）/ `after_content`（动作后完整内容）/ `before_hash` / `after_hash`（内容哈希，校验一致性、防错位回滚）/ `file_status`（同 §4.1）。

### 4.4 分级审批对象 `rdc_approval_policy`（建议名，规则可先内置于契约、不一定落表）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `operation_type` | 操作类型 | 同 §4.1 `risk_label` 取值域 |
| `risk_level` | **风险等级** | 枚举 `low` / `medium` / `high`；判定规则见 §5.4.1 |
| `intervention` | **介入强度** | 枚举 `exempt`（免审）/ `sample`（抽查）/ `strict`（强审批）；映射见 §5.4.2 |
| `decision_record` | 审批结论（运行时） | 关联审批动作与审批人；审批通过/驳回可复用 §4.5 的审核记录留痕 |

> 一次 AI 动作的**整体风险 = 其所有 hunk 风险等级的最大值**（木桶效应：只要含一个高风险 hunk，整个检查点按高风险介入）。

### 4.5 与既有 rdc 数据的关系（关联键建议）

| 本方案对象 | 关联到既有 | 建议关联键 | 边界说明 |
| --- | --- | --- | --- |
| Diff 审查 / 计划确认 / 检查点 / 审批 | `team.rdc_dev_task` | `task_id`（UUID FK） | 交互对象是研发任务的**附属证据与控制层**，不新增第二条状态写入路径；子任务状态仍只由 `DevService` 状态机写 |
| 同上 | `team.rdc_dev_subtask` | `subtask_id`（UUID FK） | 与前端/后端子任务对齐；删除子任务时交互数据级联清理，不留孤儿（沿用 `rdc_review_record` 的 `ON DELETE CASCADE` 惯例） |
| 审批结论 / hunk 决策 / 回滚事件 | `team.rdc_review_record` | **复用** `task_id` + `subtask_id`；必要时扩展 `action` 枚举 | **不新建第二套审核历史**。现有审核记录是"审核动作留痕"的唯一事实表，本方案的审批/决策留痕应扩展它（如新增 `approve_diff` / `rollback` 动作或扩展 detail 字段），而非另建表（见 §7 产品建议） |
| 需求 / 交付 | `rdc_requirements` / `rdc_delivery_record` | **本版不直接关联** | 交互层聚焦"AI 产出审查"，不越界到需求录入与交付归档；经 `task_id → requirement_id` 可间接投影 |

> 所有关联对象均带 `tenant_id`，查询先经 `repository.ScopeFilter(alias, scope)` 再叠业务条件，跨公司按 **404** 处理；`tenant_id` / 操作人只从 `scope` / 身份取，请求体不接受。

## 5. 四步交互的产品规则

### 5.1 第 1 步 · Diff 审查闭环（受控感最小单元）

布局：**中栏行级 diff + 逐 hunk 接受/拒绝 + 右栏实时预览**，配合左侧文件列表（多文件 tab）。

#### 5.1.1 逐 hunk 接受/拒绝语义

- 每个 hunk 初始 `decision = pending`；用户可切换 `accepted` / `rejected` / 回到 `pending`。
- `accepted` = 采纳这段改动；`rejected` = 明确丢弃；`pending` = 尚未处理。
- **门禁**：只要存在任一 `pending` hunk，就不允许"提交审查"；全部 hunk 都非 `pending` 时才放行提交（三态的意义）。
- 提交动作只产出"已接受的 hunk 集合"这一**契约结果**（供后续执行器应用），**本版不写真实文件**。

#### 5.1.2 右栏"应用后文件内容"计算（纯前端，不改真实文件）

- **数据源**：该文件的原始完整内容 `base`（由 Agent 产出的 before 快照给出）+ 该文件的 hunks + 当前 decisions。
- **计算口径**：定义纯函数 `applyHunks(base, hunks, decisions) → 完整文件内容字符串`：
  1. 从 `base` 的行数组出发；
  2. 仅取 `decision = accepted` 的 hunk；
  3. 按 **原始行号 `old_start` 升序**依次应用：把 `base` 中 `[old_start, old_start + old_lines)` 替换为 `new_content`；
  4. **必须使用原始行号对原始内容逐段重建**（每应用一个 hunk 后基于累积结果继续，避免行号漂移错位）；
  5. `rejected` / `pending` 的 hunk 不应用，右栏对应位置保持原样并可标注"未采纳"。
- **实时性**：任一 hunk 的 decision 变化 → 立即重算右栏内容（前端 computed/派生状态，无后端请求、无落盘）。
- **边界**：右栏只展示**文本结果**，**不改真实文件**、**不渲染运行效果**（不跑页面预览、不执行代码）。这是"应用后的文件内容"，不是"diff 高亮预览"，也不是"运行结果预览"（拍板 3）。

#### 5.1.3 多文件 tab

- 左栏列出 `files[]`；点击文件名切换中/右栏内容。
- 每个文件 tab 显示该文件 hunk 处理进度（如"3/5 已处理"），便于快速定位未决文件。
- 文件 `file_status` 以标签区分（新增/修改/删除/重命名），删除文件的 hunk 应用语义（右栏显示空/删除标记）交架构师与执行器对齐（§8 Q2）。

### 5.2 第 2 步 · 计划确认（把对齐前置）

- **时机**：在 AI **生成之前**展示 `questionnaire` + `plan_tasks`。
- **阻断**：`gate_status = blocked` 时，不进入执行、不产出 diff；问卷必答题未答完、或任务列表存在未确认项 → 用户无法"确认并进入执行"。
- **确认动作**：用户答完必答题、逐条勾选确认任务 → 点"确认计划"，服务端校验门禁条件后写 `gate_status = confirmed`、`confirmed_by` / `confirmed_at`，才允许进入执行阶段。
- **未确认不生成**：确认前不得有任何生成行为（对应图片"生成前的结构化问卷 + 可确认任务列表"）。
- **与执行的关系**：确认只表达"意图对齐完成"；**真实生成仍由隔离执行器负责**，本版不触发（执行器未就绪，§1.2）。

### 5.3 第 3 步 · 检查点回滚（敢用的心理保障）

#### 5.3.1 什么是"一次 AI 动作"

定义为：**一个已确认计划步骤的一次执行**，产生一组文件改动（对应一份 Diff 审查对象 + 一个检查点）。一个子任务可有多次 AI 动作 ⇒ 多个检查点，按时间成链。

#### 5.3.2 回滚粒度

| 粒度 | 语义 | 契约依据 |
| --- | --- | --- |
| 单 hunk | 撤销某个已接受 hunk 的采纳（decision 回到 rejected/pending，右栏内容随之重算） | hunk_id |
| 单文件 | 把某文件恢复到该检查点的 `before_content` | file_path + before_hash |
| 整个检查点 | 把该 AI 动作涉及的全部文件恢复到 `before_content` | rollback_token |

#### 5.3.3 回滚规则

- 回滚必须携带 `rollback_token`，服务端校验幂等与归属（防重复回滚、越权回滚）。
- 回滚前用 `before_hash` 校验当前内容仍是该检查点的 `after_content`（防错位回滚：若文件已被后续动作改动，需明确处理策略，见 §8 Q3）。
- 回滚**只撤销内容变更**并记录一条回滚事件；是否联动子任务状态回退，涉及现有状态机的反向流转——**现有研发状态机是严格只前进、无回退**，故此项列为 §8 Q4 待用户拍板，产品不自行决定。
- 回滚后检查点 `status` 更新为 `rolled_back` / `partially_rolled_back`，并在审核/审查历史留痕（§4.5）。

### 5.4 第 4 步 · 分级审批（避免审批疲劳）

#### 5.4.1 风险等级判定（产品规则，可先内置）

| 风险等级 | 判定规则（按操作类型） | 典型 `operation_type` |
| --- | --- | --- |
| **high（高）** | 删除文件、修改配置/密钥/权限、安装或升级依赖、数据库迁移/DDL、改 CI/CD 与安全策略、改认证鉴权代码 | `delete_file` / `config_change` / `dependency_change` / `schema_migration` / `permission_change` |
| **medium（中）** | 修改核心业务逻辑、接口签名变更、数据模型变更、跨模块重构 | `code_edit`（核心路径）/ `api_change` / `model_change` |
| **low（低）** | 新增文件、格式化、注释/文档、纯样式、新增测试 | `format` / `comment` / `doc` / `add_test` / `style` |

- **整体风险 = 检查点内所有 hunk 风险的最大值**；风险由操作类型映射而来，不由用户手填（避免绕过）。
- 无法判定类型的改动按"就高不就低"归入 `medium`（保守默认），避免高风险漏判。

#### 5.4.2 各级人工介入强度

| 介入强度 | 规则 | 适用风险 |
| --- | --- | --- |
| `exempt`（免审） | 无需人工审批，随审查提交直接通过（仍可回滚，保留 §5.3 保障） | `low` |
| `sample`（抽查） | 系统按抽样规则（如每检查点抽 1–2 个 hunk 或轮转）要求人工确认，其余默认通过 | `medium` |
| `strict`（强审批） | 必须人工逐项审批通过才能提交/应用，驳回则阻断 | `high` |

- **意图**：高频低风险改动不被审批流拖慢（免审），关键变更绝不悄悄溜过（强审批），中间地带抽查平衡（§1.4 目标 3）。
- 介入强度由 `risk_level` 自动映射，不给用户"自降风险/自免审批"的入口；审批人分派与通知属 P1（R12）。

### 5.5 四步的执行顺序与依赖

```
① Diff 审查闭环（受控感最小单元）
      ↓ 复用其 hunk/风险数据
② 计划确认（前置对齐，产出 plan_tasks + 风险预标注）   ← 图片顺序为"先 Diff 后计划"，
      ↓ 每次执行留快照                                   此处按用户图片顺序编号，产品实现可并行定义契约
③ 检查点回滚（每次 AI 动作可回退）
      ↓ 依据 hunk 风险标签决定介入
④ 分级审批（风险 → 介入强度）
```

> 图片给的是"实施顺序"（先做 Diff 闭环验证受控感，再加计划确认，再补回滚，最后分级审批）。**本版四步契约全做**，但落地实现仍建议按此顺序推进，先拿最小单元验证"受控感"。（编号沿用图片顺序，不代表运行时先后：计划确认在运行时发生于生成之前，见 §5.2。）

## 7. 权限与隔离

### 7.1 权限点（产品建议：沿用既有，不新增）

- **建议沿用现有读点**：交互能力挂在 `rdc.dev.read` / `rdc.review.read` 既有团队专区读点下，**不新增** `rdc.dev.write` / `rdc.review.write` 之类写点（沿用 02/03/04 菜单"本版不新增写点"的一贯拍板）。前端写入口不做写点判断，`me` 为 null 时按无权限处理，由上层 Gate 兜底。
- 路由链沿用：`RequireAuth → InjectScope → RequireTeamMode → RequirePermission(...)`；`RequireTeamMode` 是真边界，`TeamModeGate` 只是体验层。
- 分级审批的"强审批"是**业务规则层的介入强度**，不是新权限点；审批人资格属 P1（R12），本版只定强度不定人员。

### 7.2 数据隔离

- **平台级 team 专区**：solo（含 solo 超管）侧栏不出现、直连显示"仅团队模式可用"且不发请求；后端 `RequireTeamMode` → solo 403。
- **租户隔离**：四对象均带 `tenant_id`；所有查询先 `repository.ScopeFilter(alias, scope)` 再叠业务条件；跨公司对象按 **404** 处理，不泄漏存在性。
- **来源可信**：`source` 只能是 `agent_executor`；关联键 `task_id` / `subtask_id` 必填并校验在 scope 内可见；`tenant_id` / 操作人只从 `scope` / 身份取，请求体不接受（未知字段严格解码拒绝）。
- **路径不回显**：`file_path` 用仓库相对路径且经脱敏，绝不把绝对路径 / 原始 diff 输出回显前端（呼应交付中心 S4 脱敏）。

### 7.3 与人工审核中心的边界（产品结论：升级，不新建）

**结论：建议升级人工审核中心（03）的审核详情，而不是新建一套并行交互层。** 理由：

1. 审核中心已有"审核通过/驳回/提交确认"流程与 `rdc_review_record` 唯一留痕表，且关联键正是 `task_id` / `subtask_id`；本方案四对象沿用同键即可串起完整链路。
2. Diff 审查 / 检查点回滚 / 分级审批本质是**同一审核动作的更细粒度证据与控制**，应作为审核详情的增强视图（现有 `ReviewDetailDrawer` 已把"前端 Diff / 后端 Diff / 编辑器打开"列为后续开放占位，正是这些能力的挂载点），避免第二套审核历史、第二套状态写入口。
3. 状态真相源仍唯一：子任务状态只由 `DevService` 状态机写；交互层只记录决策/快照/审批**证据**，不新增状态写入路径（与 `rdc-dev-design.md` D2 安全底线一致）。

> 具体落地形态（在 03 菜单内扩展 vs 在 02 研发任务详情内嵌）由架构师结合接口契约定夺；产品只坚持"复用关联键与审核记录、不建第二套留痕"这条边界。此项列入 §8 Q5 请用户确认挂载位置。

## 8. 待确认问题（请 lead 转用户决策）

> 以下为产品侧需明确之处；未拍板前架构师可按本节"建议"推进，但不视为用户已决策。**产品不自行拍板改范围。**

1. **Q1｜行号口径与上下文结构**：hunk 的 `old_start`/`new_start` 采用 1-based 还是 0-based？`context_before`/`context_after` 是独立字段还是内嵌在内容行里？需与 Agent 执行器的 diff 输出格式对齐（建议 1-based、上下文内嵌带标记），否则右栏应用计算会错位。
2. **Q2｜删除/新增文件的右栏语义**：`deleted` 文件的 hunk 被接受后右栏如何呈现（空白 / 删除标记）？`added` 文件 base 为空时的应用口径？需给前端计算一个确定规则。
3. **Q3｜回滚的并发/错位策略**：若检查点之后又有新 AI 动作改了同一文件，`before_hash` 校验失败时是"禁止回滚并提示"还是"强制覆盖"？建议**禁止回滚并提示**以防误覆盖后续改动，请确认。
4. **Q4｜回滚是否联动子任务状态回退**：现有研发状态机严格只前进、无回退。回滚"AI 动作"时，子任务状态是否回退（如 `ai_completed` → 重新审查）？建议本版**只回滚内容、不动状态机**（状态回退属状态机反向流转，风险大），请确认。
5. **Q5｜交互层挂载位置**：Diff 审查 / 检查点 / 分级审批挂在 **03 人工审核中心**（升级 `ReviewDetailDrawer`）还是 **02 研发任务详情**？产品建议挂 03 以复用审核记录与关联键（§7.3），请确认。
6. **Q6｜审计留痕范围**：hunk 决策提交 / 检查点回滚 / 分级审批是否写 `team.audit_logs`？建议写（detail 含 `taskId`/`subtaskId`/`checkpointId`/动作），失败只记日志不回滚，请确认。
7. **Q7｜风险矩阵是否可内置**：本版风险等级→介入强度映射内置于契约（§5.4）是否可接受？"就高不就低"的默认 `medium` 是否认可？可配置化列为 P2。
8. **Q8｜"全做 1–4"的实现边界确认**：本版口径 = 四步**契约与规范全做**、运行时实现待执行器就绪（§1.1）。请确认这与用户"全做 1–4"的期望一致，避免被理解为"本版要看到可点的完整 UI"。

> 除上述外无阻塞性问题。**本版硬约束**：只定义数据契约与交互规范；数据源等 Agent 真产出（不写模拟数据）；不实现执行、不放假按钮；复用既有审核留痕与关联键、不建第二套。
