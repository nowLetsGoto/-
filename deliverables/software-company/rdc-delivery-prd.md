## 1. 增量目标与范围

### 1.1 产品目标（正交三条）

1. **交付证据可查**：让授权成员在一个页面看到某需求对应的 Git 提交记录与工作区状态、测试结论、验收结论，形成"这条需求交付到哪一步"的单一事实视图。
2. **交付闭环可落**：用"验收确认 → 归档"两个真实动作收口研发流程，归档时把需求状态联动为 `archived`，使需求中心与交付中心的状态首尾一致。
3. **零迁移、不破界、不越权**：在已上线能力上做最小增量，不改菜单形态、不新增权限点/写点、不触碰前 3 个菜单；Git 读取限制在命令与路径白名单内，绝不执行测试或任意 shell。

### 1.2 本次范围边界（严格遵守用户拍板，不可违背）

| 菜单 | 本次交付 | 边界说明 |
| --- | --- | --- |
| 01 需求中心 / 02 AI研发中心 / 03 人工审核中心 | ❌ **不动** | 含 V1.1 项目/图片、研发任务编排、审核与 rejected/重新研发，一律不改 |
| 04 需求交付中心 | ✅ **仅此菜单从骨架升级为做实页** | Git 记录 / 测试报告 / 验收结果 / 需求归档四个子功能做实；权限仍用 `rdc.delivery.read` |
| 菜单/权限形态 | **保持不变** | team 级平台菜单；`PermissionRDCDeliveryRead` 与 `/rdc/delivery` 菜单项均已存在，不新增、不改形态 |

**四个子功能口径（用户拍板，产品不得改写）**

| 子功能 | 本次口径 |
| --- | --- |
| Git 记录 | **服务端直读本机仓库**：配置本机仓库绝对路径，后端执行固定 `git log` / `git status` 读取提交记录与工作区状态；**只读、不写仓库、不跑测试、不执行任意命令** |
| 测试报告 | **外部 CI 生成后人工登记**：人工填写结果摘要/结论（可附报告链接或文件），平台**不自己跑任何测试命令** |
| 验收结果 | 对需求已有 `acceptance_criteria`（整段文本）**逐条确认**，记录验收结论与验收人/时间 |
| 需求归档 | 做实归档动作，**同一事务联动把 `team.rdc_requirements.status` 改为 `archived`** |

### 1.3 安全约束（硬约束，必须落到设计与实现）

> 本节是用户明确的安全底线，架构与实现不得弱化；任一不满足即视为本次交付不合格。

| 编号 | 约束 | 产品口径 |
| --- | --- | --- |
| S1 | **命令白名单** | 只允许固定、预定义的 Git 只读命令（如 `git log ...`、`git status ...`），以参数数组方式调用；**禁止接收或拼接任意 shell 字符串**，不开放"自定义命令"输入框；禁止 `git push/pull/checkout/reset/clean` 等任何写仓命令 |
| S2 | **路径白名单** | 仓库路径必须是配置允许范围内的**绝对路径**，服务端做规范化后校验前缀，拒绝 `../` 越界、符号链接逃逸与白名单外路径；前端不提供任意路径输入能力（详见 §4.2 配置分层建议） |
| S3 | **执行超时兜底** | 每次 Git 读取设固定超时（秒级），超时即终止子进程并返回友好错误，不阻塞请求、不悬挂进程 |
| S4 | **输出脱敏** | Git 输出回显到前端前必须过滤疑似凭据（token / 密码 / `Authorization` / 形如 `ghp_`、`xox`、长串十六进制密钥等）；commit message / 作者字段同样过滤；服务端日志亦不得记录原始敏感输出 |
| S5 | **只读副作用** | 服务端对仓库只有读权限语义；不写文件、不改分支、不 fetch；建议在只读能力范围内以最小权限运行 |

### 1.4 反占位与工程习惯（重申）

- 四个子功能均为**真实可用**能力：无 `TODO`、无假数据、无假按钮；任何"刷新 / 登记 / 确认 / 归档"按钮都对应真实接口与落库。
- 前端写入口不新增写点判断，统一由 `rdc.delivery.read` + `TeamModeGate` 守；后端 `RequireAuth → InjectScope → RequireTeamMode → RequirePermission(rdc.delivery.read)` 是真边界。
- 全量中文四要素注释（职责 / 输入 / 输出 / 边界）；单一职责、无冗余；按功能块逐步实现。

## 2. 用户故事

1. **作为研发负责人**，我希望按需求查看其对应的最近 Git 提交记录与工作区是否干净，以便确认代码确实已提交、交付物状态一目了然，而不必登录服务器敲命令。
2. **作为测试/QA**，我希望在外部 CI 出报告后到平台登记测试结论与摘要（必要时附报告链接），以便团队在看交付页时能看到这条需求的测试结论——且平台不会误触发任何测试执行。
3. **作为产品经理**，我希望能对着需求的验收标准逐条勾选确认、并记录验收备注，以便验收过程有据可查、结论明确到"通过/不通过"。
4. **作为研发负责人**，我希望在验收通过后执行归档，系统自动把该需求状态改为"已归档"，以便需求中心与交付中心状态一致、流程真正闭环。
5. **作为未授权成员或 solo 模式用户**，我希望看不到 `/rdc/delivery`、直连也被拦截；作为公司管理员，我希望看不到其他公司的交付记录——以便数据边界清晰、不越权。
6. **作为公司管理员**，我希望 Git 仓库只能在平台允许的根目录范围内配置，且读取过程中不会把凭据或任意命令暴露到页面——以便直读能力可用但可控。

## 4. 数据模型（PRD 层，非 DDL）

> 仅定义实体、字段语义与产品约束；表名/列类型/索引/外键/幂等 DDL 由架构师在 `schema.sql` 落实。沿用 `snake_case`、UUID 主键、`created_at`、`rdc_` 前缀、**team 专属分区**（与 `rdc_dev_task` 等一致，不进 `FOREACH team/solo` 循环）。

### 4.1 交付记录实体 `rdc_delivery_record`（建议名）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `id` | 主键 | UUID，服务端生成 |
| `requirement_id` | 绑定需求 | 指向 `team.rdc_requirements.id`，**必填**；跨租户需求拒绝；建议**一条需求一条记录**（`UNIQUE(requirement_id)`，见 §8 Q6） |
| `git_commit_sha` | 交付 commit | 最近一次读取到的 commit SHA（长度上限按 git 规范，建议存短 SHA + 全 SHA 择一，交架构师） |
| `git_commit_meta` | 提交摘要 | 作者 / 时间 / message 等展示字段——**建议不落库**、读取时实时投影（见 §5.1）；如需留存"归档时刻的快照"则落列，交架构师 |
| `git_workspace_clean` | 工作区是否干净 | 布尔，随读取实时计算；是否落库同 `git_commit_meta` |
| `test_result` | 测试结论 | 枚举 `not_registered` / `passed` / `failed`（枚举唯一来源 `openapi.yaml`，DDL 不加 CHECK） |
| `test_summary` | 测试摘要 | 人工填写的结论说明 |
| `test_report_ref` | 报告链接/引用 | 外部 CI 报告 URL（或后续附件的 relative_path）；本版以链接为主 |
| `acceptance_status` | 验收结论 | 枚举 `pending` / `passed` / `failed` |
| `acceptance_items` | 逐条验收结果 | 逐条勾选结果的投影（如按条目序号存通过/不通过）；结构由架构师定（TEXT/JSON） |
| `acceptance_note` | 验收备注 | 人工填写 |
| `accepted_by` / `accepted_at` | 验收人 / 时间 | 裸 TEXT 用户 id（沿用惯例）+ 服务端时间 |
| `archived` | 归档标记 | 布尔，默认 false；归档时置 true 并联动需求状态 |
| `archived_by` / `archived_at` | 归档人 / 时间 | 同上 |
| `creator_user_id` | 登记人 | 裸 TEXT，展示名 JOIN 投影，不冗余 |
| `tenant_id` | 公司隔离 | 从 `scope` 取，请求体不含 `tenantId` / `creatorUserId` |
| `created_at` / `updated_at` | 创建 / 更新时间 | 服务端 |

- **枚举唯一来源**放 `api/openapi.yaml`；审计如需留痕复用 `team.audit_logs`（`actor_name` 冗余、只追加），不另建审计表（是否写见 §8 Q9）。

### 4.2 仓库配置放哪（产品建议，技术实现交架构师）

平台当前**无任何 Git / 测试读取能力**：无 git 命令调用、无 go-git 依赖、无 GitLab/GitHub API 集成；`system_settings`（每公司一行）只有出站 webhook 与入站 API Key，均非"读仓库"能力。故本版需新增配置。产品建议**分两层**，避免把安全边界交给业务用户：

| 层 | 内容 | 建议落点 | 理由 |
| --- | --- | --- | --- |
| **平台级：允许根目录白名单** | 一个/多个允许的根目录（如 `/srv/repos/`） | **进程配置 `config.go` + 环境变量**（如 `RDC_GIT_ROOT`），同 `STORAGE_DIR → StorageRoot` 惯例 | 这是 S2 安全边界，只能由运维设；**绝不能让业务在 UI 改**；AGENTS.md §0 要求"唯一读环境变量处" |
| **公司级：具体仓库路径** | 该公司实际仓库的绝对路径，必须落在白名单根目录内 | 二选一（见 §8 Q3）：① 全平台共用一个仓库 → 也放 env，最简单；② 一公司一仓库 → 扩展 `system_settings` 加列，在现有平台集成设置页按公司填写 | 复用"每公司一行"隔离模型，不新建第二套配置系统（AGENTS.md §0）；配置少、加列成本最低 |

- 产品倾向：若业务上"全平台一个代码仓库"即可满足，**优先方案①（纯 env）**，本版不动 `system_settings`、不做配置 UI，最简且最安全；若确需一公司一仓，再走方案②。此决策交用户/架构师（§8 Q3）。

### 4.3 验收标准是否拆条（产品建议）

需求侧 `acceptance_criteria` 是**整段 TEXT**、无结构化条目 ID。用户口径为"逐条确认"。产品建议：

- **本版采用"展示层拆条"**：读取整段文本，按**换行/序号**在页面上拆成可视条目，每条一个勾选框；不新增条目表、不改需求录入（成本最低、不越界到 01 需求中心）。
- 验收记录存"逐条结果投影 + 整段备注"，全部条目处理完才能提交验收结论。
- 拆分规则（按换行还是按 `1./-` 序号）、以及是否允许"部分条目不通过"时提交，见 §8 Q2 待确认。

## 5. Git 读取的产品口径

### 5.1 展示字段

| 区块 | 字段 | 来源 | 说明 |
| --- | --- | --- | --- |
| 提交列表 | 最近 N 条 commit：短 SHA、作者、提交时间、message（首行 + 可展开全文，脱敏后） | 固定 `git log`（参数数组，限制条数如 10–20） | 按时间倒序；条数见 §8 Q7 |
| 工作区状态 | 是否干净（clean / dirty），dirty 时可展示变更文件数量（不展示文件内容） | 固定 `git status --porcelain`（只判断有无输出/计数） | 只读判断，不展示 diff 内容 |
| 分支（可选） | 当前分支名 | `git status -b` 或同次调用附带 | 视实现成本决定，见 §8 Q7 |
| 读取信息 | 最近读取时间、读取结果状态 | 服务端 | 便于判断是否需手动刷新 |

> 以上字段均为**只读投影**；不提供 commit 展开 Diff、不提供切换分支/回滚等操作入口。

### 5.2 刷新频率

- **本版手动刷新**：详情页提供"刷新 Git 记录"按钮，点击才触发服务端读取（真实接口，带 loading / 失败重试）。
- **不做自动轮询**：本地仓库 IO 有超时成本、状态变化由研发操作驱动，自动轮询价值低且放大风险（S3）。
- 进入详情是否自动读一次：建议**打开详情时读取一次** + 手动刷新按钮（产品建议，交架构师确认实现口径）。

### 5.3 读取失败的展示（文案口径）

| 场景 | 前端文案（建议） | 处理 |
| --- | --- | --- |
| 仓库未配置 | "尚未配置 Git 仓库路径，请联系管理员。" | 不显示刷新按钮（避免无效点击）；后台记录告警 |
| 路径不存在 / 不可访问 | "仓库路径不可访问，请检查配置。"（**不回显完整绝对路径**，避免信息泄漏；详情由服务端日志记录） | 提供重试 |
| 路径越界 / 非白名单 | "配置的仓库路径不在允许范围内。" | 不重试（配置问题，需管理员修） |
| 非 Git 仓库 | "配置的路径不是有效的 Git 仓库。" | 不重试 |
| 读取超时 | "读取 Git 记录超时，请稍后重试。" | 提供重试 |
| 其他命令失败 | "读取 Git 记录失败，请稍后重试。" | 提供重试 |

- 所有错误文案统一经脱敏（S4）；任何情况下**不得把原始命令输出/完整路径/凭据回显到前端**。

## 6. 验收与归档流程

### 6.1 验收确认

- **前置条件（建议）**：关联交付记录与需求存在、需求状态**非 `archived`**；验收人具备 `rdc.delivery.read`。
  - 关联研发/审核进度作为**参考信息展示**（子任务整体状态、是否存在 `rejected`），本版建议**不强制**"全部研发/审核完成"才能验收——是否强制见 §8 Q1。
- **动作**：逐条勾选验收标准结果 → 填写验收备注 → 选择结论（通过 / 不通过）→ 提交；写入 `acceptance_*` 字段与验收人/时间。
- **约束**：结论为"不通过"时**不允许归档**（归档硬校验验收结论为"通过"）；验收可重新提交以覆盖结论（本版不做多版本验收历史，如需留痕见 §8 Q9）。

### 6.2 归档

- **前置校验（服务端硬校验）**：交付记录存在、需求未归档、**验收结论为通过**。不满足返回 400，不写库。
- **联动时机**：归档写在**一个事务**内——置 `archived=true`、写归档人/时间，并**同步把 `team.rdc_requirements.status` 改为 `archived`**；任一步失败整体回滚，杜绝"交付显示已归档、需求仍是研发中"的不一致。
- **不可逆性**：归档是交付闭环终点，属**不可逆高危操作**——UI 需二次确认并写清影响面（"归档后需求将标记为已归档，不可在本版撤销"），符合 AGENTS.md §6。
- **能否撤销**：本版建议**不可撤销**；撤销会引入需求状态回退与交付状态机反向流转，列为 P1 / §8 Q4 待确认。

### 6.3 流程全景

```
选择需求 → [Git 记录(直读/手动刷新)] → [测试报告(人工登记)] → [验收(逐条确认/通过)] → [归档(事务联动需求 status=archived)]
                                                                  └ 不通过 → 不可归档，可重新验收
```

> 产品说明：四个子功能在页面上并列呈现为交付闭环的不同证据段，但**归档是唯一的状态.writer**，其余为证据登记；不要求严格按序完成（除"归档需在验收通过后"这条硬约束）。

## 7. 权限与隔离

### 7.1 权限点不变（用户拍板）

- `/rdc/delivery` 仍由 **`rdc.delivery.read` 单点守护**：菜单可见性、路由守卫、列表/详情/Git 刷新/测试登记/验收/归档**全部用它**。
- **不新增 `rdc.delivery.write`**：写入口不做写点判断（有意沿用 02/03 菜单"本版不新增写点"的拍板惯例）；`me` 为 null 时按无权限处理，由上层 Gate 统一承担。
- 后端路由组：`RequireAuth → InjectScope → RequireTeamMode → RequirePermission(rdc.delivery.read)`；前端 `TeamModeGate` 外层 + `PermissionGate(rdc.delivery.read)`（现状已如此，保持）。

### 7.2 数据隔离

- **平台级 team 专区**：solo（含 solo 超管）侧栏不出现、直连显示"仅团队模式可用"且不发请求；后端 `RequireTeamMode` 是真边界（solo → 403）。
- **租户隔离**：交付记录表带 `tenant_id`；所有查询先经 `repository.ScopeFilter(alias, scope)` 再叠业务条件；跨公司交付记录/需求按 **404** 处理，不泄漏存在性。
- **绑定需求隔离**：登记/验收/归档时服务端复校 `requirement_id` 存在且属当前 `tenant`，越界拒绝。
- **归属字段** `tenant_id` / `creator_user_id` 只从 `scope` / 身份取；请求体不接受这些字段（未知字段按现有严格解码规则拒绝）。

### 7.3 命令/路径白名单的产品层约束

- 前端**不提供**任意命令输入框、不提供任意仓库路径输入框（防止把 S1/S2 的边界前移到不可控的用户输入）。
- 用户可见的只有固定操作：刷新 Git 记录、登记测试、确认验收、归档；"配置仓库路径"属运维/管理员能力，按 §4.2 分层落点，不在交付页内开放。
- 脱敏（S4）在服务端输出边界统一处理，前端不做二次拼接原始输出。

## 8. 待确认问题（请 lead 转用户决策）

> 以下为产品侧认为需明确之处；未拍板前架构师可按本节"建议"推进，但不视为用户已决策。

1. **Q1｜验收是否强制研发/审核完成**：建议**参考展示、不强制**，仅要求需求非 `archived`；归档前才硬校验验收通过。若用户希望"研发全部完成且无 rejected 才能验收"，需明确 rejected 子任务的处理（是否必须先重新研发）。
2. **Q2｜验收标准拆分规则与不通过处理**：建议按**换行/序号**展示层拆条（不改需求表）；请确认拆分依据，以及"部分条目不通过"时是否允许提交验收为"不通过"（建议允许，但不通过不可归档）。
3. **Q3｜仓库配置落点**：建议全平台共用一个仓库时**纯 env 配置**（最简、最安全，不动 `system_settings`、不做配置 UI）；若一公司一仓库则扩展 `system_settings` 加列并做设置页。请确认①是否一公司一仓、②本版是否需要配置 UI（产品倾向本版不做 UI）。
4. **Q4｜归档是否可撤销**：建议本版**不可撤销**；若用户要"撤销归档"，需定义需求状态回退规则（会触及状态机反向流转），请明确。
5. **Q5｜测试报告是否本版支持附件上传**：建议本版做"结果摘要 + 外部链接"即可（最简）；若必须支持上传报告文件，需新增文件类型/大小白名单（`rdc_requirement_attachment` 仅图片，不适用），请确认是否本版包含。
6. **Q6｜交付记录粒度**：建议**一条需求一条交付记录**（`requirement_id` 唯一，各段结果就地更新）；若需多次交付历史则放开为多条，请确认。
7. **Q7｜Git 展示细节**：建议展示最近 10–20 条 commit、工作区是否干净、是否附带分支名；请确认条数与是否要分支。
8. **Q8｜审计留痕范围**：Git 刷新一般不写审计（读操作）；**测试登记 / 验收确认 / 归档**是否写 `team.audit_logs`（便于追溯谁在何时改了交付结论）？产品建议：验收与归档必写、测试登记建议写，失败只记日志不回滚。请确认。

> 除上述外无阻塞性问题。四个子功能均为真实能力、不含假按钮；S1–S5 安全约束为本版硬底线。
