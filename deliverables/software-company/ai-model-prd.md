## 0. 用户拍板（不可违背，本 PRD 全部口径以此为准）

1. **API Key 加密后入库（最新变更，推翻早前 env 方案）**：模型 Key **不写仓库、不写 `.env`**；用 **AES-GCM** 加密后存入数据库，加密主密钥走 env `RDC_MODEL_ENCRYPTION_KEY`；界面 / 日志 / 接口响应**只显示掩码，绝不回显完整 Key**，绝不写日志。用户贴在对话中的那个 Key 视为**已泄露**，须由 lead 提示用户轮换；**本 PRD 不含该 Key 明文**，任何实现与文档均不得出现。
   - 派生要求：加密主密钥经 `internal/config/config.go` 这一唯一 `os.Getenv` 出入口读取，并按 AGENTS.md「新增环境变量」配方同步 `.env.example` 与 README / deploy；密钥缺失或长度非法时服务应**启动即失败**（fail fast），不得静默降级为明文存储。
2. **隔离维度 = 公司（tenant）**：每家公司配置自己的模型列表 / 默认模型 / 思考 / 上下文；与现有 `system_settings` 按 tenant 一行、`ScopeFilter` 隔离的惯例一致；**超管可按公司查看 / 代配**。
3. **统一调用接口 = 后端 Go 服务接口**（如 `ModelService.Chat`）：内部模块注入使用，**不暴露前端任意调用**；按「公司 + 场景」取配置并调用 LLM。
4. **可配置项 = 思考模式开关 + 上下文长度**：每个模型可配是否开启深度思考（reasoning effort）+ 上下文窗口大小（max context tokens），按公司保存；**配置结构必须可扩展**，后续能加更多选项（如 temperature、top_p、超时）。
5. **本版要真实发起一次 LLM 调用实测**：用加密入库的 Key 打 scnet `/chat/completions`，会消耗少量 token（需用户知悉并授权）；实测结果作为验收证据，失败要给出明确错误分类。

用户一贯要求：代码简单优雅、单一职责、无冗余、完整中文注释；不清楚 / 不合理的列入「待确认问题」交 lead 转用户，**不自行拍板改范围**；反占位（禁止 TODO / 假数据 / 假按钮）；安全上 Key 绝不回显、绝不写日志。

## 1. 增量目标与范围

### 1.1 产品目标（正交三条）

1. **让模型配置集中可管**：管理员可按公司维护一份可用的模型清单（首版落地 scnet / DeepSeek-V4.1-Flash-1017），设置默认模型，并逐模型配置思考模式与上下文长度；敏感 Key 加密入库、仅掩码可见。
2. **让全平台用模型只有一条路**：提供一个后端 Go 服务接口，内部模块（含 AI 交互层）按「公司 + 场景」取配置并统一调用 LLM，避免各处散落 base_url / Key / 协议细节。

## 2. 用户故事

1. **作为公司管理员**，我希望按本公司维护一份模型清单、把 scnet 的 DeepSeek 模型接入进来，以便本公司各模块有统一的模型可用，而不用每个功能各配一套。
2. **作为公司管理员**，我希望填写模型 API Key 后系统加密保存、界面只显示掩码，以便我不用把密钥明文暴露在页面或日志里，也满足安全合规。
3. **作为公司管理员**，我希望为本公司的模型设置默认项，并逐模型配置「是否开启深度思考」和「上下文长度」，以便不同模型按业务需要工作，且这些配置随公司隔离。
4. **作为公司内部模块开发者（如 AI 交互层）**，我希望注入一个后端服务接口，按「公司 + 场景」就能拿到配置并调用 LLM，以便我不再关心 base_url、Key、协议与思考 / 上下文细节。
5. **作为超管**，我希望按公司查看 / 代配各公司的模型配置，以便在子公司未配置或配置有误时能统一运维，同时不破坏公司间隔离。
6. **作为未授权成员 / solo 模式用户**，我希望看不到也无法直达 `/rdc/models`；作为普通公司成员，我希望看不到别的公司的模型配置与 Key——以便数据边界清晰、不越权、不泄露密钥。

## 4. 数据模型（PRD 层，非 DDL）

> 仅定义实体、字段语义与约束；表名 / 列类型 / 索引 / 外键 / 幂等 DDL 由架构师在 `schema.sql` 落实。沿用 `snake_case`、UUID 主键、`created_at` / `updated_at`、`rdc_` 前缀、**team 专属分区**（沿用 RDC 已定决策：`RequireTeamMode` 是模式边界，不为用不到的 solo 造表）。Key 密文与扩展配置落库细节见 §5.3 / §5.4。

### 4.1 模型配置实体 `rdc_ai_model`（建议名）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `id` | 主键 | UUID，服务端生成 |
| `tenant_id` | **公司隔离** | 从 `scope` 取，请求体不含 `tenantId`；列表 / 详情 / 调用查询统一经 `ScopeFilter` 隔离；跨公司按 404 |
| `name` | 模型显示名（用户可见） | 必填，≤ 100 字；公司内可重名（不设唯一，见 §8 Q2） |
| `model_id` | 模型标识（调用时传给 LLM 的 model 参数） | 必填，如 `DeepSeek-V4.1-Flash-1017` |
| `provider` | 供应商 / 接入源标识 | 枚举建议 `scnet` 等；首版预置 scnet |
| `protocol` | 协议类型 | 枚举 `openai` / `anthropic` / `openai_responses`；首版只用 `openai`，其余预留（§5.4） |
| `base_url` | API 基址 | 必填，如 `https://api.scnet.cn/api/llm/v1`；保存前做 URL 合法性校验；调用时据此拼 `/chat/completions` |
| `api_key_ciphertext` | **加密后的 Key 密文** | AES-GCM 密文（含 nonce / tag 的存储格式由架构师定）；**绝不明文入库**；解密仅发生在 `ModelService` 调用链内存中 |
| `is_default` | 是否本公司默认模型 | 每公司至多一条为 `true`；切换默认在同一事务内互斥（§5.1） |
| `thinking_enabled` | 思考模式开关 | bool，是否开启深度思考；默认 `false`；参数注入语义见 §5.2 |
| `context_tokens` | 上下文长度（max context tokens） | 正整数，取值语义见 §5.2 |
| `extra_config` | **扩展配置 JSON** | 存后续可加的选项（reasoning effort 级别 / temperature / top_p / 超时等）；首版可为空 `{}`；结构可扩展、向后兼容（§5.4） |
| `capabilities` | 能力标签（预留） | 数组如 `文本生成` / `深度思考` / `视觉理解`；首版只展示不参与调度（§5.4、§8 Q3） |
| `enabled` | 启用 / 停用 | bool，停用的模型不参与默认选择与调用；删除策略见 §8 Q4 |
| `created_at` / `updated_at` | 创建 / 更新时间 | 服务端 |

### 4.2 默认模型选择

- **不单独建表**：默认模型就是 `rdc_ai_model.is_default = true` 的那一条，`ModelService` 按「公司 + 场景」优先取默认、再取启用项（§7.1）。
- **唯一性由事务保证**：同一 `tenant_id` 下至多一条 `is_default=true`；设置默认时先清本公司其它记录的 `is_default` 再置目标记录，全程在同一事务内（沿用主数据「先清后写、全量覆盖」惯例）。
- **默认与启用联动**：停用一个当前默认模型时，须先处理默认指向（自动落到本公司另一启用模型，或要求先指定新默认——见 §8 Q4）。

## 5. 产品规则

### 5.1 默认模型唯一性与切换

- 每家公司**至多一个默认模型**；首个启用的模型自动成为默认（若的实现选择如此，见 §8 Q4），或由管理员显式指定。
- 切换默认：用户在列表点「设为默认」，服务端事务内把本公司其它模型 `is_default` 置 `false`、目标置 `true`；返回后列表只显示一条默认标记。
- 未配置任何默认且存在启用模型时，`ModelService` 的兜底行为见 §7.2；完全无启用模型时返回明确错误（§7.4）。

### 5.2 思考模式与上下文长度取值语义

| 配置项 | 字段 | 语义 | 取值 / 默认 |
| --- | --- | --- | --- |
| 思考模式开关 | `thinking_enabled` | 是否在调用时开启深度思考（reasoning / reasoning effort） | bool，默认 `false`；开启时由 `ModelService` 按协议把参数注入请求（OpenAI 兼容协议下的具体参数名由架构师按 scnet 实际支持情况确定，见 §8 Q6） |
| 上下文长度 | `context_tokens` | 传给 LLM 的最大上下文窗口（max context tokens） | 正整数，需校验在合理区间（建议 1024 ~ 模型上限，上限见 §8 Q6）；作为调用参数注入 |

- 两项均**按公司 + 按模型**保存；前端表单提供与 WorkBuddy 自定义模型一致的选择 / 开关交互，保存后即时生效于下一次调用。
- 取值语义是「配置意图」，最终以 scnet 实际接受的参数为准：若某模型不支持深度思考或某上下文值超出其上限，`ModelService` 应在实测 / 调用出错时给出明确提示（§7.4），而不是静默丢弃。

### 5.3 Key 掩码规则（安全硬约束）

- **展示**：任何向前端返回的 DTO 中，Key 字段都是掩码串，**绝不返回完整 Key**。掩码规则建议：仅保留前缀标识与末 4 位，中间以 `****` 代替（如 `sk-****wxyz`）；长度不足时全部打码。具体投影在 service 完成（repository 只返回密文，handler 不接触明文）。
- **写入 / 更新**：表单中 Key 输入框初始值为掩码占位；用户不修改直接提交时**保持原密文不变**（前端传空或特殊标记表示"不更新"，由后端识别，见 §8 Q7）；只有填了新值才重新加密覆盖。禁止把掩码串当成真 Key 回写。
- **日志**：任何日志（含审计 detail、错误堆栈、HTTP access log）**不得出现完整 Key 或密文**；审计 detail 只记「某模型的 Key 被更新」这一事实，不记值。
- **加密主密钥**：`RDC_MODEL_ENCRYPTION_KEY` 缺失 / 长度非法时服务启动即失败，不允许降级为明文或弱加密；轮换主密钥的迁移方案不在本版（见 §8 Q8）。

### 5.4 扩展配置如何留口子

- 模型配置中保留一个 **JSON 扩展段**（`extra_config`），用于承载首版之后才明确的选项，例如 reasoning effort 级别、temperature、top_p、请求超时、自定义请求头等。
- **向后兼容**：`ModelService` 读取扩展段时，未知键一律忽略（不报错），缺失键用内置默认；因此后续新增选项不需要改表结构、不需要迁移历史数据。
- **校验边界**：首版扩展段可以是空对象 `{}`，也不在 UI 暴露具体项（避免假配置入口）；它只是数据结构上的预留口子，由后续迭代按需填入并在那时补 UI。扩展段的字段白名单 / 校验强度见 §8 Q3。
- **能力标签**（`capabilities`）同理预留为数组，首版只做只读展示、不参与模型选择逻辑。

### 5.5 调用失败展示

- 配置页的「测试连接 / 实测」按钮若调用失败，按 §7.4 的错误分类给出**中文可读提示**，例如：未配置 Key、Key 无效 / 鉴权失败（401/403）、网络不可达 / 超时、模型不存在（404）、参数不被支持（400，如思考 / 上下文值越界）、供应商限流（429）、响应格式异常。
- 提示信息**不得包含 Key、密文或完整请求体**；只显示状态码、错误类别与可操作的建议（如"请检查 Key 是否有效""请调小上下文长度"）。
- 失败只是调用侧结果，**不回滚任何已保存的配置**；配置保存与调用实测是两个独立动作。

## 6. 页面设计、权限与隔离

### 6.1 主页面 `/rdc/models`（AI模型）

- 标题「AI模型」+ 简短说明（"按公司配置可用的 AI 模型与调用参数，供平台各模块统一使用"）。
- 列表列：模型名称 / 模型 ID / 供应商 / 协议 / base_url / 默认标记 / 思考开关 / 上下文长度 / Key 掩码 / 状态（启用 / 停用）/ 更新时间。
- 主操作「新增模型」「测试连接 / 实测」；行操作「编辑」「设为默认」「启用 / 停用」「删除」。**这些写入口都按写点隐藏**（见 §6.2），读点只负责页面可见。
- 服务端分页（页码进 URL）、`States` 三态、空列表空态卡片不挂分页条；UI 组件来自 `@seakoi/console-kit` 根入口、筛选 / 切换用 `Controls.Segmented`。

### 6.2 权限点设计（新增读点 + 写点建议）

- **读点（必加）**：`rdc.model.read`，作为菜单 `ViewPermission` 与路由守卫；归入「研发中心」权限分组，`Label` 如"查看 AI 模型"。同步 `contract.Permissions`、`Menus`、`AllMenuKeys`、`DefaultMenuKeys`（`AutoGrantBuiltin=false`，与其余 4 个 RDC 菜单一致，由管理员显式勾选授权）。
- **写点（建议新增）**：`rdc.model.write`，守护新增 / 编辑 / 删除 / 设默认 / 实测等**所有写操作**（含后端 `RequirePermission` 与前端按 `can(me, 'rdc.model.write')` 隐藏写入口）。
  - **理由**：本模块涉及 API Key 与全局调用配置，属敏感操作；与需求中心的 `rdc.requirement.read/write` 读写分离惯例一致。这一点**有意不同于** `rdc.dev.read` 的"仅读点"决定——因为研发任务编排是低敏感编排动作，而模型 / Key 配置是高敏感配置。
  - 菜单 `Actions` 挂 `rdc.model.write`（对齐 `rdc.requirement` 菜单的 `Actions` 写法），表单路由 / 写操作用 `PermissionGate(rdc.model.write)`。
  - **是否新增写点属产品建议，需用户拍板**，见 §8 待确认 Q1；若用户决定不新增写点，则全部操作统一用 `rdc.model.read` 守，前端不做写点判断。

### 6.3 隔离与超管代配

- **team 专区**：solo（含 solo 超管）侧栏不出现、直连 `/rdc/models` 显示"仅团队模式可用"且不发请求；后端 `RequireTeamMode` 是真正边界（solo → 403）。菜单 `AutoGrantBuiltin=false`，普通成员默认看不到。
- **租户隔离**：模型表带 `tenant_id`；列表 / 详情 / CRUD / 实测查询统一先经 `repository.ScopeFilter(alias, scope)` 再叠加业务条件；跨公司模型按 **404** 处理，不泄漏存在性；归属字段从 scope 取，请求体不接受 `tenantId`。
- **超管按公司代配**：超管 `scope.All` 下需能**选定目标公司**查看 / 代配其模型配置。产品规则：
  - 超管访问列表时需带一个「目标公司」选择（下拉 / 查询参数），未指定时不默认展示某一家的 Key 配置，避免误操作；选定公司后以该 `tenant_id` 作为隔离过滤条件。
  - 代配写操作审计 detail 记 `target_tenant_id` 与操作者，明确"超管代某公司配置"。
  - 非超管的公司管理员只能在自己 `tenant` 内操作（沿用现有 ScopeFilter 行为），不提供公司切换入口。
  - 具体超管选公司的交互与后端 scope 投影对接方式见 §8 Q2。

### 6.4 审计

- 模型配置的**新增 / 编辑 / 删除 / 设默认 / Key 更新 / 实测触发**写入 `team.audit_logs`（沿用 `audit.Service.Record(ctx, actor, action, objectType, objectID, detail, ip)`）。
- detail 只记非敏感事实（如 `modelId`、`provider`、动作类型、`target_tenant_id`），**不记 Key 明文 / 密文 / 扩展配置中的敏感项**。
- 审计写入失败**只记日志、不回滚业务**（沿用现有惯例）。

## 7. 统一调用接口的产品语义

> 本接口是**后端 Go 服务接口**（如 `ModelService.Chat`），供内部模块注入使用；**不注册为前端可直调的 HTTP 路由**。URL / DTO 等契约细节由架构师在接口契约设计中确定，本节只定义产品语义。

### 7.1 按「公司 + 场景」取配置

- 调用方传入至少两项：**公司标识（tenant，通常由 scope 注入，调用方不显式传 Key）** 与 **场景标识（scene）**。
- 取配置的优先级（产品口径）：
  1. 若该公司在目标场景下有显式指定的模型（场景级配置，本版为空，见 R12），用它；
  2. 否则用该公司的**默认模型**（`is_default=true` 且启用）；
  3. 该公司无默认但有启用模型时，按 §7.2 处理。
- `ModelService` 内部完成：按 tenant 隔离取模型配置 → 解密 Key（仅内存）→ 按协议 + 思考开关 + 上下文长度组装请求 → 调用 LLM → 返回结果。**Key、base_url、协议细节完全不向调用方暴露**。

### 7.2 未配置默认时的行为

- 公司无任何模型配置 / 无启用模型：返回一个明确的业务错误（配置缺失类，见 §7.4），**提示管理员去 `/rdc/models` 配置**，而不是静默空调用或抛底层 NPE。
- 无默认但有多个启用模型：**产品建议**取列表中第一个启用模型作为兜底并在结果中标记"使用非默认模型"，便于排查；此兜底口径需用户确认（§8 Q4）。若用户不接受兜底，则改为直接报"未设置默认模型"。
- 场景指定的模型不存在 / 被停用：返回明确错误（配置缺失类），不静默回退到默认（避免调用方以为用了指定模型）。

### 7.3 首版协议与调用范围

- 首版只实现 **OpenAI 兼容协议**（scnet 的 `/chat/completions`）。Anthropic / OpenAI Responses 协议在结构中预留、本版不实现（R10）。
- 入参最小集：tenant（scope 注入）+ scene + 对话消息；思考开关 / 上下文长度 / 扩展配置由服务端按模型配置注入，调用方不逐次覆盖（避免绕过公司配置）。
- 实测与统一接口复用**同一套调用实现**，保证"实测通过 = 接口可用"，不写第二份调用逻辑（呼应 AGENTS.md「不建第二套 HTTP 客户端」）。

### 7.4 错误分类（面向调用方与页面提示）

| 类别 | 触发 | 建议返回口径 |
| --- | --- | --- |
| 配置缺失 | 公司无模型 / 无启用模型 / 无默认且不接受兜底 / 场景模型不存在 | 明确业务错误，提示去配置页；不暴露底层细节 |
| 鉴权失败 | 上游 401 / 403（Key 无效或泄露已失效） | "密钥无效或已失效，请更新 Key"；**不含 Key** |
| 参数错误 | 上游 400（模型不存在 / 思考或上下文参数不支持 / 越界） | "模型或参数不被支持，请检查模型 ID 与思考 / 上下文配置" |
| 限流 / 过载 | 上游 429 / 5xx | "供应商繁忙或限流，请稍后重试" |
| 网络 / 超时 | 连接失败、读超时 | "网络不可达或调用超时，请稍后重试" |
| 响应异常 | 响应非预期格式 / 空响应 | "供应商响应异常" |

- 所有错误**不得回显 Key、密文或完整请求体**；上游返回的原始 error body 若要记录，须先脱敏且仅写服务端日志、不返回前端。
- 调用失败不影响已保存配置；调用方收到的是分类后的错误，不是上游原始报文。

## 8. 待确认问题（请 lead 转用户决策）

> 以下是产品侧认为需明确之处；未拍板前架构师可按本节"建议"推进，但不视为用户已决策。**Q1 为唯一硬阻塞项**，其余不阻塞 PRD 成立。

1. **Q1（阻塞）｜是否新增写点 `rdc.model.write`**：产品建议**新增读点 `rdc.model.read` + 写点 `rdc.model.write`**，读写分离、敏感操作受控（§6.2）。请确认；若用户坚持"只加读点"，则全部操作用 `rdc.model.read` 守、前端不做写点判断。此项直接影响权限目录、菜单 `Actions`、路由守卫与前端隐藏逻辑，须先定。
2. **Q2｜超管按公司代配的交互与 scope 投影**：超管列表是否需要「目标公司」下拉 / 查询参数？未指定时展示空态还是平台兜底？代配时后端 scope 如何切到目标公司（沿用现有平台级 scope 机制还是需要新参数）？产品建议见 §6.3。
3. **Q3｜扩展配置范围与能力标签**：`extra_config` 首版是否需要列入任何具体字段（reasoning effort 级别 / temperature / 超时等），还是纯空 `{}` 预留？能力标签（`文本生成 / 深度思考 / 视觉理解`）首版是否只展示、不参与调度？字段白名单与校验强度请确认。
4. **Q4｜默认兜底与删除 / 停用联动**：(a) 无默认但有启用模型时是否按 §7.2 取第一个启用模型兜底？(b) 删除 / 停用当前默认模型时，是自动改指另一启用模型，还是强制先指定新默认？(c) 删除用软删（`enabled=false`）还是硬删？产品建议：启用兜底 + 软删 + 默认被停用时强制先指定新默认。
5. **Q5｜对话中泄露 Key 的处理**：用户贴在对话里的 Key 视为已泄露。产品建议：lead 已提示用户**轮换该 Key**；本 PRD / 代码 / 测试 / 数据中均不含其明文；实测须用轮换后的新 Key。请确认轮换已完成再执行实测。
6. **Q6｜思考 / 上下文的具体参数与上限**：scnet / DeepSeek-V4.1-Flash-1017 是否支持深度思考、对应参数名 / 取值（如 reasoning effort 级别）、上下文上限具体数值？产品建议由架构师查 scnet 文档确定并在 §5.2 区间内校验；若该模型不支持思考开关，界面是否仍展示该配置项（避免假配置）请用户确认。
7. **Q7｜Key 更新交互**：编辑时 Key 输入框留空表示"不更新"（保留原密文）——这个约定是否符合用户预期？是否需要在表单上明确文案说明"留空即不修改"？
8. **Q8｜加密主密钥轮换**：`RDC_MODEL_ENCRYPTION_KEY` 若需轮换，存量密文如何迁移？产品建议本版不做轮换功能，仅保证首次配置正确、密钥妥善保管；后续迭代再考虑。

> 除 Q1 外无阻塞性问题。本版硬约束重申：**Key 不写仓库 / 不写 .env / 加密入库 / 仅掩码可见 / 绝不回显 / 绝不写日志**；隔离维度为公司（tenant）；统一接口为后端内部 Go 服务接口、前端不可直调；只做配置管理 + 统一调用 + 一次真实实测，不做 Agent 执行与模型训练。
