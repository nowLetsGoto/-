## 1. 增量目标与范围

### 1.1 产品目标（正交三条）

1. **让需求可归属**：每条需求明确落在公司的一个现有项目上，使需求从"平台级流水记录"变成"可归因到项目"的工程输入，支撑后续按项目追踪交付。
2. **让需求可表达**：允许负责人为需求附多张图片（设计稿 / 截图 / 标注），让文字描述之外的视觉信息进入需求，减少来回沟通。
3. **零迁移、零破界**：在 V1.0 已上线能力上做最小增量，不改菜单形态、不改权限模型、不改路径规范，不触碰其余 3 个研发中心菜单。

### 1.2 本次范围边界

| 范围 | 本次交付 | 说明 |
| --- | --- | --- |
| 01 需求中心 | ✅ **仅此菜单改动** | 关联项目 + 图片上传 + 列表筛选 + 详情展示 |
| 02 AI研发中心 / 03 人工审核中心 / 04 需求交付中心 | ❌ **不动** | 保持 V1.0 骨架页现状，本次不改路由、页面、权限 |
| 菜单形态 | **保持平台级** | 需求中心仍在「研发中心」一级分组下，`scope:'platform'`、`envScoped:false`，**不放进 `/p/:key/*`，不改造成项目内菜单** |
| 权限模型 | **保持不变** | 继续用 `rdc.requirement.read` / `rdc.requirement.write`，**不引入项目角色、不改用项目角色判定** |

### 1.3 形态重申（关键，推翻 V1.0 决策）

> V1.0 §6 / D5 曾定"需求不与分发项目挂钩"。**本增量正式推翻该条**：需求新增必填归属项目。

- **菜单仍是平台级**：入口与路由不变，仍是 `/rdc/requirements`（平台级），不是 `/p/:key/rdc/requirements`。
- **项目是"归属字段 + 筛选维度"，不是"访问边界"**：
  - 新建时**必须选项目**（必填归属）；
  - 列表按项目筛选（一个下拉，单选）；
  - 权限判定**仍走 `rdc.requirement.read/write` 权限点**，与项目角色无关。
- 与 AGENTS.md「平台接口刻意忽略 `?project=`，只用人员角色判定」不冲突：此处 `projectId` 是**业务归属与筛选条件**，不是权限判据；接口仍是平台级接口，不按项目取项目角色。
- **现有项目来源**：`team.projects`（App 包的一级归属，含 `key` / `name`，team 分区），列表接口 `GET /api/v1/projects?pageSize=0`（全量，供下拉选项）。

### 1.4 新增 / 修改清单（概念级）

| 类型 | 内容 |
| --- | --- |
| 新增字段 | 需求主表 `project_id`（必填）、展示字段项目名 `projectName`（关联投影） |
| 新增实体 | 需求附件 `rdc_requirement_attachment`（一需求多图） |
| 新增能力 | 图片上传（多图）、图片访问、详情页图片预览 |
| 修改页面 | 列表页（项目筛选 + 项目列）、新建页（必选项目 + 图片上传区）、详情抽屉（项目名 + 图片网格） |
| 不新增 | 权限点、菜单项、一级分组、项目角色关联、`/p/:key/*` 路由 |

## 2. 用户故事

1. **作为研发负责人**，我在需求中心新建需求时必须选择一个所属项目，以便每条需求都能明确归到具体项目、后续可按项目追踪。
2. **作为研发负责人**，我在新建需求时可以一次上传多张设计稿 / 截图 / 标注图，以便用视觉信息完整表达需求，不必在别处来回传图。
3. **作为开发工程师**，我在需求列表可以按"项目"筛选、再叠加关键字搜索，以便快速收敛到我负责项目下的需求。
4. **作为开发工程师**，我点开需求详情时能看到所属项目名和图片预览网格，以便在一个地方看全文字与视觉信息。
5. **作为公司管理员**，我看不到、也选不到其他公司的项目和图片，以便跨公司数据严格隔离、不越权。

## 4. 数据 / 字段设计（PRD 层，非 DDL）

> 仅定义实体、字段语义与约束；表名 / 列类型 / 分区 / 索引 / 外键 / 幂等 DDL 由架构师在 `schema.sql` 落实。风格沿用 `snake_case`、UUID 主键、`created_at`，`rdc_` 前缀、team 分区（沿用 V1.0 决策 D3）。

### 4.1 需求主表 `rdc_requirements`（增量字段）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `project_id` | 所属项目，**新增必填** | 指向 `team.projects.id`，必须存在且属于当前公司（tenant）；新建/筛选的核心字段 |
| `projectName` | 展示字段：项目名 | 建议由关联 `team.projects` 投影得到（沿用 V1.0 `creatorName` 的 JOIN 投影惯例，不冗余存列）；具体由架构师定 |
| `req_key` | 需求编号 | **格式不变**：`REQ-YYYYMMDD-NNN`，服务端生成、唯一、创建后不可改 |
| 其余字段 | `id` / `title` / `description` / `status` / `acceptance_criteria` / `creator_user_id` / `tenant_id` / `created_at` | 全部沿用 V1.0，不改语义 |

> 存量兼容：`project_id` 允许为空（不带 NOT NULL 强制历史行），用于承载 V1.0 无归属数据；新写入一律必填。是否用默认值 / 回填策略由架构师定。

### 4.2 新实体 `rdc_requirement_attachment`（需求图片附件）

| 字段 | 语义 | 约束 / 规则 |
| --- | --- | --- |
| `id` | 主键 | UUID，服务端生成 |
| `requirement_id` | 所属需求 | 指向 `rdc_requirements.id`，一需求对多附件 |
| `file_name` | 原始文件名（展示用） | 经清洗（如 `CleanFileName`），不用于拼路径 |
| `content_type` | 图片 MIME | 白名单内，如 `image/png` |
| `file_size` | 字节数 | ≤ 单张上限（§4.3） |
| `relative_path` | **本地 storage 相对路径** | 相对 uploads 的规范路径（形如 `{env}/.../{id}.{ext}`），由 storage 包 `RelativePath`/`FinalPath` 生成、`SafeResolve` 校验；**禁止另起路径规范或自行拼接** |
| `created_at` | 创建时间 | 服务端 |

> 实体名以 team-lead 建议的 `rdc_requirement_attachment` 为准（V1.0 规划稿曾写作复数，落地名由架构师最终确定）。本实体从 V1.0 的 P1 预留**提前到 V1.1 的 P0** 落地，但仅限图片类型。

### 4.3 图片约束（建议值，供架构师落实为常量与校验）

| 项 | 建议值 | 说明 |
| --- | --- | --- |
| 允许格式 | `png` / `jpg` / `jpeg` / `webp` / `gif` | 白名单，按 `content_type` + 扩展名双重校验；其余一律拒绝 |
| 单张大小上限 | **5 MB** | 超限明确中文提示，不进入提交 |
| 单需求数量上限 | **9 张** | 前端拦截 + 后端复校，防绕过 |
| 扩展名来源 | **由图片格式白名单派生**，不取用户文件名 | 沿用 storage「扩展名只由白名单映射」惯例（见 `paths.go` §5 边界） |
| 存储位置 | 现有本地 `storage/uploads/...` | 复用 storage 包路径生成与安全校验能力；目录分段由架构师定，不改现有路径规范 |

### 4.4 接口影响（概念级，供架构师写契约）

| 接口 | 增量 |
| --- | --- |
| `GET /api/v1/rdc/requirements` | 查询参数增 `projectId`（可选筛选）；响应项增 `projectId` / `projectName`；附件是否随列表返回由架构师定（详情页再取亦可） |
| `POST /api/v1/rdc/requirements` | 请求体增 `projectId`（必填）+ 图片（multipart）；创建需求 + 附件同事务/同流程落库 |
| `GET /api/v1/rdc/requirements/{reqKey}` | 响应增 `projectId` / `projectName` / `attachments[]`（含 `file_name` / `content_type` / `file_size` / 可访问的图片地址） |
| 图片访问 | 提供按 `relative_path`（或附件 id）读取图片的能力，读取必须经 `SafeResolve` 前缀校验，防 `../` 越界 |

> 契约变更顺序遵循 AGENTS.md §4：`openapi.yaml` → 契约常量/DTO → `make gen:api` → 前端 API → 测试；不得手改 `schema.d.ts`。

## 5. 页面设计

### 5.1 列表页 `/rdc/requirements`

- **新增「项目」筛选**：下拉单选，选项来自 `GET /api/v1/projects?pageSize=0`（只列本公司项目），默认"全部项目"；与状态筛选（`Controls.Segmented`）、关键字搜索可叠加。
- **新增「项目」列**：展示需求所属项目名；存量无归属数据显示"未归属项目"占位文案。
- 其余沿用 V1.0：服务端分页（页码进 URL）、三态组件、点需求 ID 开详情抽屉、"新建需求"按钮按 `rdc.requirement.write` 显示。

### 5.2 新建页 `/rdc/requirements/new`

- **新增「所属项目」必选下拉**：复用同一项目列表接口；未选不允许提交，有即时校验提示。
- **新增图片上传区**：使用 `Upload.Dragger`，`beforeUpload` 返回 false（非法文件返回 `LIST_IGNORE`），**禁止组件自动上传**；前端先做格式/体积/数量校验；显示缩略图与可移除项（提交前移除仅影响本次选择）。
- 其余字段（标题 / 描述 / 状态默认待评审 / 验收标准选填）沿用 V1.0；需求 ID 仍由服务端生成。

### 5.3 详情抽屉（列表点击需求 ID 打开）

- **新增项目名展示**：与需求基本信息同区展示。
- **新增图片预览区**：缩略图网格，点击可预览大图；无图片时不渲染空网格（存量需求兼容）。
- 其余只读字段与状态标签沿用 V1.0；本版仍不提供编辑 / 删除按钮（避免假操作）。

### 5.4 上传时机（产品建议，技术实现由架构师定）

> 参考现有包上传的 `stage` / `commit` 两步体验，但需求图片更简单。这里给产品建议，不规定实现。

- **建议：随需求创建一次性提交**（"先建需求再补图"作为备选）。理由：
  1. 图片是需求输入的一部分，用户心智是"填完表单 + 附图，一次提交"，两步会让流程变碎；
  2. 需求图片量小（≤9 张、单张 ≤5MB），一次性提交成本可接受；
  3. 避免"建了需求却没传图"的中间态与孤儿文件；
  4. V1.0 新建页本就是一步式表单，一次性提交对它改动最小。
- 若架构师评估一次性 multipart 提交在事务一致性 / 失败补偿上代价过高，可退化为"先建需求拿到 id，再以该 id 为归属上传图片"，但需保证失败时不留孤儿需求 / 孤儿文件，并对用户呈现为一次连续操作。
- 无论哪种时机，`relative_path` 生成与访问都必须走 storage 包既有能力（`FinalPath` / `RelativePath` / `SafeResolve`），不得另起一套路径规范。

## 6. 权限与隔离

### 6.1 权限点不变（重申）

- 需求中心仍由 `rdc.requirement.read`（读）与 `rdc.requirement.write`（写）守护，**不新增权限点、不改授权方式、不引入项目角色**。
- 列表 / 详情守 `rdc.requirement.read`；新建（含图片上传）守 `rdc.requirement.write`。
- 路由仍是平台级 team 专区：`RequireAuth → InjectScope → RequireTeamMode → RequirePermission(...)`；solo 不可见、不可访问；前端写入口用 `can(me, ...)` 控制，`me` 为 null 按无权限处理。
- 项目只是**归属与筛选字段**，不作为权限判据：平台级接口不按项目取项目角色，避免与 AGENTS.md 的项目角色模型混淆。

### 6.2 跨公司隔离（重申并强化）

- **前端**：项目下拉只列本公司项目（复用现有项目列表接口的可见范围），不显示、也选不到其他公司项目。
- **后端必须校验**（不可只信前端）：
  1. 新建时校验 `project_id` 对应的项目**存在**且**属于当前 `tenant`**；否则返回 **400（非法项目）或 404（不存在）**，不得写入；
  2. 列表按项目筛选时，筛选条件叠加租户范围，跨租户项目筛不出他人需求；
  3. 详情与图片访问同样受租户范围约束：非本公司需求 / 附件按 404 处理，不泄漏存在性；
  4. 图片读取必须经 `SafeResolve` 前缀校验，防 `relative_path` 被篡改成 `../` 越界读取。
- 归属 `tenant_id` 仍从 `scope` 取（沿用 V1.0 D5），请求体不含 `tenantId` / `creatorUserId`；超管平台级可见范围沿用 V1.0 既有约定，不做特殊分支。
