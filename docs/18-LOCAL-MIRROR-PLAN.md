# 本机留底 + R2 按需同步 · 方案设计

> 2026-11-26 · 基于用户提出的「本机存全部、R2 只留近期」方案优化
> 目标：用本机磁盘换 R2 免费额度，让可用版本容量从 9GB 提升到磁盘上限
> 状态：方案已定，待实施

## 1. 要解决的问题

当前直传包（> 100MB）只在 R2，本机不留副本。
后果有两个：

1. **R2 是唯一副本**——淘汰一旦删掉对象，包就彻底消失
2. **可用容量被 9GB 卡死**——本机磁盘 69GB 可用，却只能用 9GB

目标形态：**本机是权威副本，R2 是可回收的缓存。**

## 2. 现状核实（实施前提）

| 事实 | 数值 / 代码位置 |
| --- | --- |
| R2 配额 | `retentionMaxBytes = 9 GiB`（`build_retention.go:31`），取 9 是给 10GB 免费额度留抖动余量 |
| 版本数上限 | `retentionMaxVersions = 66` |
| 直传包本地副本 | **无**。`Create` 的直传分支只做 `StatObject` + `os.Remove` 占位文件 |
| 普通上传包本地副本 | 有。`os.Rename` 到 `storage/uploads/{env}/{platform}/{id}.apk` |
| 淘汰是否检查本地副本 | **否**。直接 `DeleteObject`，无任何存在性检查 |
| 磁盘可用 | 69 GB（已用 85%） |

**当前数据实测**：4 个直传包全部无本地副本，2 个普通上传包有。

### 现存注释与实现不一致（需一并修正）

`build_direct_upload.go:128` 写「整包落盘推迟到 Create：届时直接从 R2 下载到正式目录」，
但 `Create` 里没有任何下载逻辑，只有删除。这段注释会误导后来者，实施时一并改掉。

## 3. 数据模型：只加一个字段

```sql
ALTER TABLE team.builds ADD COLUMN IF NOT EXISTS local_state TEXT NOT NULL DEFAULT 'absent';
ALTER TABLE solo.builds ADD COLUMN IF NOT EXISTS local_state TEXT NOT NULL DEFAULT 'absent';
```

| `local_state` | 含义 | 生命周期 |
| --- | --- | --- |
| `absent` | 本机无副本，待拉回 | 直传提交后立即进入 |
| `pulling` | 后台拉回中 | 拉取期间 |
| `present` | 本机已归档 | 常态（目标） |
| `failed` | 拉回失败 | 待巡检重试 |

**为什么不新建 `r2_status`**：现有 `r2_state` 已有 `pending` / `synced` / `evicted`，
语义完全覆盖。再加一套并行状态字段必然漂移——两处描述同一件事，改一处忘另一处。

## 4. 上传流程

```
① 前端选包 → POST /builds/upload-ticket（带 project）
② 浏览器 PUT 直传 R2（字节不经过服务器，速度最快）
③ POST /builds/stage-from-r2   Range 读 manifest 解析元信息
④ POST /builds (Commit)
     r2_state    = 'synced'    ← 已有对象，用户立即可下载
     local_state = 'absent'    ← 待拉回
     立即返回成功，不阻塞等待下载
⑤ 提交后立即异步拉回（goroutine），失败由巡检兜底
     成功 → local_state = 'present'
     失败 → local_state = 'failed'
```

**与当前实现的差异**：第 ④ 步不再 `os.Remove` 占位文件后就算完，
而是写状态并触发第 ⑤ 步。

## 5. 拉回本机（核心新增逻辑）

### 5.1 触发时机（两层，兼顾及时与可靠）

| 层 | 时机 | 作用 |
| --- | --- | --- |
| 即时 | 提交成功后立即起 goroutine | 用户无需等待，几秒到几十秒内完成 |
| 兜底 | 2 小时巡检扫描 `local_state IN ('absent','failed')` 和卡死的 `pulling` | 服务重启丢失 goroutine、或下载中途被杀时补上 |

`pulling` 是中间态，进程在下载中途被杀后状态会永远停在那里（实测卡过 18 小时）。
抢占时写 `local_pulling_at`，巡检把超过 30 分钟、或时间戳为空的存量 `pulling`
当成卡死重新入队；筛选条件与抢占条件必须一致，否则会出现「捞出来却抢不到」的空转。
巡检的单包与整轮还各有 panic 保护：一个坏数据只影响本轮，不会让 goroutine 静默消失。

不引入 Redis / Celery：单机部署、任务是「下载一个文件」，
一个 goroutine 加巡检兜底已经足够可靠，引入队列只会让部署与排障更复杂。

### 5.2 落盘路径

复用现有 `Paths.FinalPath(environment, platform, id, ext)`，
与普通上传走同一套 `storage/uploads/{env}/{platform}/{id}.apk`。

这样两条上传路径的产物完全一致，下载逻辑无需分支。

### 5.3 安全要求（缺一不可）

| 要求 | 原因 |
| --- | --- |
| 先写临时文件再 rename | 半截文件不能出现在 uploads 下，否则会被当成有效副本 |
| 落盘后校验大小 | `StatObject` 的大小与本地文件大小必须一致 |
| 磁盘空间预检 | `可用空间 < 包大小 × 1.2` 则跳过并记日志，避免写满磁盘 |
| 并发上限 | 同时最多拉 2 个，避免占满带宽影响用户下载 |

## 6. 淘汰流程（改动最关键的一处）

### 6.1 你选择的策略：先拉回，再删 R2

```
巡检发现超额
  ↓
候选包本机有副本？
  ├─ 有 → 直接删 R2 对象，r2_state = 'evicted'
  └─ 无 → 先把对象拉回本机
           ├─ 成功 → 删 R2 对象，local_state = 'present'，r2_state = 'evicted'
           └─ 失败 → 跳过本轮，下轮重试；不删 R2（否则包彻底丢失）
```

**这条安全闸是方案成立的前提**：没有它，淘汰一个「本机也没副本」的包
等于永久丢数据——R2 删了、本机没有、数据库记录还在，用户点下载永远 404。

### 6.2 淘汰后保留 r2_key

当前 `MarkEvicted` 会清空 `r2_key`：

```sql
SET r2_key = '', r2_bytes = 0, r2_state = 'evicted'
```

改为**保留 key**，只改状态：

```sql
SET r2_bytes = 0, r2_state = 'evicted', r2_synced_at = NULL
```

原因：「同步到 R2」需要知道推到哪个 key。清了就得重新生成，
而重新生成可能丢失归属信息（`{租户}/{项目}/direct/` 前缀）。

**连带改动**：下载判断不能再看 `r2_key <> ''`，必须改看 `r2_state = 'synced'`，
否则会 302 到已删除的对象。这一处改动必须与 §6.2 同时上线，不能分开。

### 6.3 磁盘成为新瓶颈时的处理

本机磁盘满了怎么办？这是新方案引入的新风险，必须有兜底：

```
拉回前预检：可用空间 < 包大小 × 1.2 → 跳过，记日志
```

**不做自动删本地包**——本机是权威副本，自动删就等于丢数据。
空间不足时应该人工清理（删掉不要的历史版本），而不是系统替他决定。

## 7. 「同步到 R2」接口

```
POST /api/v1/builds/{id}/sync-to-r2
```

**只对 `r2_state = 'evicted'` 的包显示按钮**（用户已确认）。

```
1. 校验 local_state = 'present'，本机文件存在
     → 否则返回 400「本机无副本，无法同步」
2. 幂等：若 r2_state 已是 'synced' → 直接返回成功
3. 用保留的 r2_key 上传本机文件到 R2
4. 成功 → r2_state = 'synced', r2_bytes = 实际大小, r2_synced_at = now()
5. 失败 → 返回错误，状态不变（可重试）
6. 写审计日志：谁在什么时候重推了哪个包
```

## 8. 界面表现

| 位置 | 显示 |
| --- | --- |
| 包列表 | `r2_state = 'evicted'` 的包显示「同步到 R2」按钮 |
| 包列表 | `local_state = 'pulling'` 显示「归档中」轻提示 |
| 包列表 | `local_state = 'failed'` 显示警示图标，hover 提示「本机归档失败，将自动重试」 |
| 容量条 | 增加一行本机占用：`本机 8.2 GB / 69 GB 可用` |

容量条加本机用量是必要的：R2 只占 9GB，但本机可能涨到几十 GB，
用户需要知道磁盘还剩多少。

## 10. 实施顺序（必须遵守）

改动 5 与 6 **必须同一次上线**。若只改 5 不改 6，淘汰后 `r2_key` 还在，
下载会 302 到已删除对象；若只改 6 不改 5，逻辑不冲突但白改一趟。

建议分三批：

```
第一批（安全地基）
  1 加字段 → 5 保留 key → 6 下载判断改看 r2_state
  验证：淘汰一个包后，下载仍能用本地副本成功

第二批（留底能力）
  2 Commit 写状态 → 3 拉回逻辑 → 4 巡检补拉
  验证：直传一个包，几秒后本机出现文件

第三批（人工干预）
  7 sync 接口 → 8 前端按钮 → 9 容量条
  验证：淘汰一个包 → 点同步 → R2 恢复 → 下载走 CDN
```

### 第二批的实现要点

- **抢占用条件 UPDATE**：`WHERE local_state <> 'pulling'` 靠影响行数做互斥。
  先查后写之间有窗口，两个执行体会同时判定「该我拉」，同一对象被下载两份。
- **先写临时文件再 rename**：直接写正式路径会在中断时留下半截文件，
  而下载逻辑只看「文件是否存在」，半截文件会被当成有效副本发给用户。
- **并发上限 2**：单机部署下用户下载会与拉回抢带宽。
  占槽放在抢占之前——先标 pulling 再排队会让状态在等带宽期间一直显示「归档中」。
- **淘汰前查文件而非查状态**：`local_state` 可能因崩溃停在 pulling，
  也可能因手工清理磁盘而与事实不符。只有真 stat 到文件且大小相符才敢删 R2。
- **本地已有文件则跳过下载**：加列前没有 local_state，加列后一律默认 absent，
  与磁盘实际不符。巡检据此自然对齐存量，不必另写迁移脚本。

### 第二批的实测结果

| 场景 | 结果 |
| --- | --- |
| 本地已有文件 | 日志「无需拉回」，状态转 present |
| 本地文件被删 | 真下载，39 字节对象落地 |
| 磁盘预检 | 68.4 GB 可用，正常放行 |
| 并发抢占 | 第二次抢不到（避免双份下载） |

### 第三批的实现要点

- **只允许 evicted 重推**：synced 的对象还在桶里，重推是白传 119MB；
  pending/failed 属于上传流程中间态，由后台镜像负责。
  两个入口都能改状态会让它们互相覆盖。
- **状态准入抽成纯函数** `checkResyncable`：混在 SyncToR2 里时，
  任何验证都得先备好数据库、对象存储与完整权限链，成本高到没人愿意写测试。
- **沿用原有 r2_key 而非重新生成**：那个 key 带着 `{租户}/{项目}/direct/` 前缀，
  是判断对象归属的唯一线索。重新生成会造出孤儿。
- **必须 POST**：这个动作真实上传对象、改服务端状态，
  用 GET 会让浏览器预取、代理缓存、甚至一个 `<img>` 标签触发它。
- **幂等**：synced 时直接返回当前状态而非报错——用户可能连点两次，
  或页面状态已过期。

### 第三批的实测结果

| 场景 | 结果 |
| --- | --- |
| 淘汰包重推 | HTTP 200，`r2State` → `synced`，`r2Bytes` 为真实大小 |
| 重复调用 | HTTP 200，幂等不报错 |
| 本机副本丢失 | HTTP 400「本机副本已丢失，无法同步到对象存储」 |
| 已同步的包 | 拒绝并提示「无需重推」 |

### 第四批的实现要点

- **本机占用必须按 local_state 过滤，不能累加 file_size**。
  实测：13 条记录合计 1478MB，磁盘只有约 1024MB——差额来自 4 个直传包，
  它们记录里有大小，但字节只在 R2、本机没有文件。按状态过滤才与磁盘对得上。
- **两段进度条而非一条**：R2 是 9GB 配额，超额会触发淘汰，需要红色警示；
  本机上限取决于磁盘剩余，超额只会让留底失败、不会删数据。
  混在一条里会让「9GB 用了 100%」与「磁盘用了 5%」看起来像同一种危机。
- **磁盘可用查不到就整段不显示**（服务端返回 0）。显示 0 会让人以为磁盘满了，
  比不显示更糟。
- **StorageUsage 从 openapi 派生**：原先手写了一份，这批加四个字段时差点漏改。
  两处描述同一结构，漂移只是时间问题。

## 11. 验收要点

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 直传 119MB 包并提交 | 立即返回成功；几秒内本机出现文件，`local_state=present` |
| 2 | 提交后立即看列表 | 可下载（走 R2 直链） |
| 3 | 关掉服务再启动 | 巡检把 `absent` 的包补拉回本机 |
| 4 | 造超配额触发淘汰 | 候选包先拉回本机，成功后 R2 对象消失、`r2_state=evicted` |
| 5 | 淘汰后下载 | 走本地流式，成功 |
| 6 | 对已淘汰包点「同步到 R2」 | `r2_state` 变回 `synced`，下载改走 CDN |
| 7 | 磁盘不足时拉回 | 跳过并记日志，不写满磁盘、不删本地文件 |
| 8 | 淘汰时本机也无副本 | 先拉回；拉回失败则跳过本轮，**绝不删 R2** |

## 12. 需要明确接受的代价

| 代价 | 说明 |
| --- | --- |
| 本机磁盘会长 | 不再只占 9GB，而是随版本数增长。当前 69GB 可用，按 110MB/包算可存约 600 个 |
| 淘汰变慢 | 「先拉回再删」意味着一次 119MB 下载，比原来直接删慢几十秒 |
| 首次打开慢 | 拉回期间若 R2 已被淘汰（极端情况），用户需等待本地文件就绪 |
| 状态字段变多 | 多一个 `local_state`，列表与详情都要兼顾 |

**替代方案**：若嫌淘汰变慢，可改为「本机无副本则跳过淘汰」——
不下载、不删除，只记日志等人工处理。代价是那个包继续占 R2 空间。
用户已选择「先拉回再删」，本方案按此定稿。
