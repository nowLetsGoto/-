## 2. ⚠️ 必须解决的冲突：Q3 会让直传包彻底失效

### 实测证据

```
✅ 有本地: 57fabb39...apk（早期普通上传）
✅ 有本地: 8d4c8fa7...apk（早期普通上传）
❌ 无本地: 42337309...apk  → r2=direct/0bb62f67...
❌ 无本地: 71f3052e...apk  → r2=direct/043a7573...
❌ 无本地: 499d45de...apk  → r2=direct/1d828823...
❌ 无本地: af919c8d...apk  → r2=direct/ec449a0f...
```

**原因**：早前为修复"发布接口慢"，直传包（浏览器直接 PUT 到 R2）不再落盘到本机，
`Create` 只写数据库 + 记录 `r2_key`，本地无文件。

**后果**：Q3 规定"淘汰只删 R2 不删数据库"——对这 4 个包，删掉 R2 对象后：

- CDN 直链 → 404
- 本地回退（`streamFile` 的 `os.Open`）→ 文件不存在，返回 NotFound
- 数据库记录还在 → 用户看到包、点下载、永远失败

**这不是理论风险，是当前数据里已经存在的 4 个包。**

### 三个可选解法

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 淘汰时若本地无文件，**不删 R2**，只记日志标记"无法淘汰：无本地副本" | 该包占着 R2 空间，但至少能下载 |
| **B** | 淘汰前先把 R2 对象下载回本地，再删 R2 | 淘汰变成一次 119MB 下载，慢且耗本机带宽 |
| **C** | 改回"直传也落盘本地"，恢复双副本 | 发布接口重回 50 秒慢，且本机磁盘翻倍 |

**推荐 A**：淘汰的目的是省 R2 空间，但如果删了会导致包不可用，那不如不删——
留一个"候选但跳过"的标记，等你人工决定（可配合 Q5 的人工删除）。

## 3. Q2 的额外影响：凭据按租户独立

"Cloudflare 配置数据根据每个租户进行登录使用"意味着：

- 每个租户有自己的 R2 桶 + Access Key
- 9GB 预算是**每租户独立判断**
- 需要新增租户级配置表（现在 R2 配置是全局环境变量）

需要新增：

```
tenant_storage_config 表：tenant_id / account_id / bucket / access_key / secret_key / quota_bytes
```

以及 `R2` 客户端从"单例"改成"按租户获取"。

**❓需确认**：现在只有一个租户（默认公司），是否**先按全局 9GB 实现**，
租户级凭据留到真正多租户时再做？否则本轮改动会翻倍。

## 4. 实现方案（按 Q1/Q3/Q9 定稿）

### 4.1 字段语义调整

| 字段 | 调整 |
| --- | --- |
| `r2_state` | 新增值 `evicted`（R2 已淘汰但数据库保留） |
| `r2_bytes` | 淘汰后置 0，表示"不在 R2" |
| `pin_kind` | 仅 `manual` |
| `last_accessed_at` | 保留（Q9），淘汰排序主依据 |

### 4.2 淘汰算法（Q1 平台级 66）

```
输入：全平台所有包（跨项目、跨环境、跨平台）
1. 排除 pin_kind != '' → 固定永不淘汰
2. 排除本地无副本的（§2 方案 A）
3. 按 last_accessed_at ASC, created_at ASC 排序
4. 若总量 > 66 或 已用 > 9GB：
     从最旧开始，逐个标记为淘汰候选，直到满足 66 且 ≤ 9GB
输出：待淘汰 id 列表
```

**注意 Q1 的语义变化**：全平台 66 个，意味着"项目 A 传 40 个 + 项目 B 传 30 个 = 70 个"，
会有 4 个被淘汰。

### 4.3 执行淘汰（Q3：只删 R2）

```
对每个候选：
1. 若本地无副本 → 跳过并记日志（§2 方案 A）
2. 删 R2 对象
3. UPDATE r2_state='evicted', r2_bytes=0
4. 写审计日志（不删数据库行）
```

### 4.4 人工删除（Q5）

平台界面删包时：删 R2 对象 → 删本地文件 → 删数据库行（含级联 share）。
现有 `Delete` 已实现（任务 1），无需额外改动。

### 4.5 容量展示（Q6/Q7）

放在「应用」菜单（`/apps`）页头部：
- 进度条：已用 X GB / 9 GB
- 预估：还能传 N 个包（按平均包大小）
- 超限时红字提示

# 追加需求：每晚 12 点从 R2 反向同步到数据库

> 2026-11-26 18:00 用户提出
> 场景：① 数据库误删/回滚后的恢复；② 补录未入库的对象

## 7. 技术前提核实结果

实测孤儿对象 `direct/689a0049-...apk` 的 R2 元数据：

```
ContentType:        application/vnd.android.package-archive
ContentLength:      124927223
LastModified:       2026-11-26 06:59:55 UTC
ContentDisposition: (空)
自定义 Metadata:    (空 —— 没有任何业务元数据)
```

**R2 对象当前不含任何业务字段**，直接同步只能恢复出残缺记录：

| 数据库字段 | 能否恢复 |
| --- | --- |
| `file_size` / `platform` / `file_ext` / `r2_key` | ✅ 能 |
| `created_at` | ⚠️ 近似（LastModified 是上传完成时间） |
| `app_name` / `package_id` / `version` / `build_number` | ❌ 不能 |
| `changelog` / `original_file_name` / `owner_user_id` | ❌ 不能 |
| **`project_id`**（NOT NULL + 外键） | ❌ **不能，阻塞** |
| `environment` | ❌ 不能 |

## 8. 关键架构约束：key 无法携带项目

上传链路决定了项目信息出现得太晚：

```
① IssueUploadTicket  只知道 fileName / size / contentType —— 无项目
② 浏览器 PUT 到 R2   key 在此刻已固定
③ StageFromR2        只知道 uploadToken —— 无项目
④ Create(commit)     项目在这里才由 resolveProject 确定
```

`UploadTicketInput` 只有 3 个字段（fileName / size / contentType），前端也没有项目上下文。
**因此"改 key 携带项目"需要改前端与契约，不是纯后端改动。**

## 9. 推荐方案：commit 后补写元数据

既然 `SetContentDisposition` 已证明可以用 `CopyObject` 改写对象元数据，
就在 `Create` 成功后（项目、环境、应用名全部已知）补写完整业务元数据。

### 9.1 写入的元数据

```go
// CopyObject with MetadataDirectiveReplace，写入以下 x-amz-meta-*：
meta-project-key    = 项目 key（如 world2-1）
meta-environment    = test / prd / hotfix / pre
meta-app-name       = 景田
meta-package-id     = uni.UNIeebddc7
meta-version        = 26.9.1
meta-build-number   = 873
meta-owner          = 上传者 userID
meta-build-id       = 包 id（同时也用于校验 key 与记录对应）
meta-original-name  = 原始文件名
```

体积约 300 字节/对象，可忽略。

### 9.2 与现有补写合并

`prewarmCDNAsync` 里已经在调 `SetContentDisposition`（一次 CopyObject）。
把业务元数据合并进同一次 CopyObject，**不增加额外请求**。

### 9.3 每晚同步流程

```
01. 列出 R2 所有对象
02. 查数据库所有 r2_key
03. 差集 = 孤儿对象
04. 对每个孤儿：
     a. 读 x-amz-meta-project-key 等元数据
     b. 若元数据完整 → 按原 project/environment/appName 等重建数据库记录
     c. 若元数据缺失（历史对象）→ 记入"待人工确认"清单，不自动入库
05. 写同步报告到日志
```

### 9.4 幂等性

- 用 `r2_key` 做唯一判据：已存在的跳过
- 重建的记录 `id` 用 key 里的 uuid（`direct/{uuid}.apk` → uuid）
- 若该 uuid 已存在于数据库 → 跳过（说明没丢）

### 9.5 历史对象的处理

现有 9 个对象都没有业务元数据。同步脚本会跳过它们并列出清单，
需人工指定项目后再入库（对应 Q5 的人工处理原则）。

若你希望它们也能自动恢复，可以现在补跑一次元数据写入——
但需要人工确认每个对象属于哪个项目。

## 10. 三件事的依赖关系

```
补写元数据（§9.1）
    ↓ 前提
每晚同步（§9.3）
    ↓ 协同
Q3 淘汰只删 R2 不删数据库
```

注意 **Q3 与同步的关系**：Q3 淘汰后数据库记录仍在，所以同步不会把它当孤儿。
同步真正处理的是"数据库记录不存在但 R2 对象存在"——即误删或回滚。

## R2 对象 key 新结构

```
{tenantID}/{projectKey}/direct/{token}.{ext}

例：a1b2c3d4-.../world2-1/direct/ec449a0f-....apk
```

**收益**：
- 对象自带租户 + 项目归属，每晚反向同步可仅凭 key 还原
- 多租户天然隔离（不同租户的对象在不同前缀下）
- 仍用 UUID 作文件名，不可枚举，安全性不变

**兼容性**：数据库存的是完整 `r2_key`，下载直接用它，新旧格式并存不影响功能。
历史对象（`direct/xxx.apk`、`test/android/xxx.apk`）无归属信息，反向同步时需人工确认。

## 实现细节

- `UploadTicketInput` 新增 `project` 字段（前端上传时取 `useCurrentProject().key`）
- `IssueUploadTicket` 提前调 `resolveProject` 校验项目存在与访问权限——
  避免用户传完 300MB 才在 commit 阶段发现项目无效
- 租户 ID 从 `authctx.ScopeFrom(ctx).TenantID` 读取
- 删除已废弃的 `DirectKeyOf`（无调用点，且路径拼法已过时）

## 9GB 配额校验规则（待实现）

```sql
-- 每租户已用 = 该租户下所有包的 r2_bytes 之和
SELECT COALESCE(SUM(b.r2_bytes), 0)
FROM builds b
JOIN projects p ON p.id = b.project_id
WHERE p.tenant_id = $1 AND b.r2_state = 'synced'
```

上传前预检：`已用 + 新包大小 > 9GB` 则拒绝，提示"存储空间不足，请先清理"。

淘汰：按 `last_accessed_at ASC, created_at ASC` 排序，从最旧开始删 R2 对象直到满足 9GB 与 66 个。

**注意**：淘汰只删 R2、不删数据库（Q3）。若该包本地无副本，淘汰后不可下载——用户已确认接受此风险。
