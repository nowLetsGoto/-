## 任务 1：修 `Delete` 不删 R2 对象的泄漏

**解决什么问题**：用户手动删包后，本地文件和数据库行都删了，但 R2 上的 119MB 对象永不删除。
每删一个包就永久浪费 119MB，且无法通过任何界面看到。

**根因**：`service/build_mutation.go:66` 的 `Delete` 只做 `os.Remove`，
没调用已存在的 `storage/r2.go:240 DeleteObject`（该方法注释写着"淘汰时调用"，但全仓零调用点）。

**动作**：
1. `Delete` 在删本地文件后，若非空 `r2_key` 则调 `DeleteObject`
2. 失败只记日志（数据库行已删，由任务 5 的巡检兜底）

**验证**：删一个包 → 查 R2 对象列表，该 key 消失。

**独立可做，风险最低，建议第一个做。**

## 任务 2：加 7 个治理字段

**解决什么问题**：现在数据库只知道"有没有 r2_key"，不知道同步是否成功、对象多大、是否允许淘汰、
多久没被下载。没有这些信息，淘汰算法无法判断该删谁。

**动作**：`team.builds` / `solo.builds` 各加 7 列（`schema.sql` 用 `%1$I` 模板，一次生成两分区）：

| 字段 | 解决什么 |
| --- | --- |
| `r2_state` | 区分 pending/synced/failed/local_only，让 Worker 知道该重试谁 |
| `r2_synced_at` | 同步时间，用于重试退避与诊断 |
| `r2_bytes` | 对象真实字节，预算计算与用量统计的唯一依据 |
| `pin_kind` | 标记永不淘汰的版本（`''` / `manual` / `release`） |
| `pinned_at` | 何时钉住，UI 展示用 |
| `pinned_by` | 谁钉的，留痕 |
| `last_accessed_at` | 最近下载时间，淘汰优先级的第二判据 |

**验证**：`\d team.builds` 出现 7 列；存量 14 个包不受影响（全有默认值）。

**❓ 待确认**：
- `pin_kind` 是否只需要 `manual` 一种语义？我想保留 `release`（重要版本）但可以砍掉。
- `last_accessed_at` 每次下载都写库会增加一次 UPDATE。是否接受这个写入成本？
  （替代方案：不存该字段，淘汰只按 `created_at`）

## 任务 3：淘汰算法（纯函数）

**解决什么问题**：没有任何机制限制版本数量，项目长期发版会无限堆积直到撑爆 10GB 免费额度。

**动作**：新建 `service/build_retention.go`，一个纯函数：

```
输入：全部分组（含 size / created_at / pin_kind / last_accessed_at）
1. 排除 pin_kind != '' → 钉住的永不删
2. 每组按 created_at DESC 保留前 66，其余进候选
3. 若全局占用 > 9GB，候选按 last_accessed_at ASC 逐个扣减直至达标
输出：待淘汰 id 列表（只读，不执行删除）
```

**为什么纯函数**：可单测边界（全钉住、空组、超额、恰好 66），且不碰数据库便于推理。

**验证**：单测覆盖 5 种边界；构造 70 个包的测试数据，断言输出 4 个最旧 id。

**❓ 待确认**：Q1（66 的计数范围）、Q2（9GB 归属）

## 任务 4：执行淘汰

**解决什么问题**：任务 3 只算出该删谁，不会真的删。需要一个可靠的执行器。

**动作**：对每个待淘汰 id，严格按序执行：

```
1. 删 R2 对象（DeleteObject，已幂等）
2. 删本地文件（os.Remove，容忍不存在）
3. 删数据库行（级联删 build_shares）
4. 写审计日志（记录 id/版本/大小/触发原因）
```

**顺序为什么不能乱**：先删数据库行，一旦后续步骤失败，信息就丢了，无法重试也无法追溯。
按上述顺序中途失败时数据库行还在，下次巡检会再试。

**验证**：手动触发淘汰 → 数据库、本地、R2 三处同时消失；审计日志有记录。

**❓ 待确认**：Q3（是否通知上传者）

## 任务 5：Worker 定时巡检

**解决什么问题**：靠发布时触发不够——进程重启会丢失异步任务，历史数据也没人处理。
例如现在 R2 上那 2 个孤儿对象，没有任何机制会发现它们。

**动作**：`main.go` 起一个 goroutine，`time.Ticker` 每小时跑一次：

```
1. 补齐 r2_state = pending/failed 的对象（重试同步）
2. 执行淘汰（任务 3 + 4）
3. 扫描 R2 孤儿对象（有对象无数据库记录）→ 处理
```

**为什么不引入队列/调度框架**：单机部署、每小时一次、任务量小，`Ticker` 足够。
引入 Redis/Celery 之类会为 4 个小任务增加部署复杂度。

**并发控制**：进程内 `sync.Mutex` 防重入。单机不需要分布式锁。

**验证**：手动把某包 `r2_state` 改成 `failed` → 等一个周期 → 变回 `synced`。

**❓ 待确认**：Q4（巡检间隔）、Q5（孤儿对象怎么处理）

## 任务 6：存储用量统计接口

**解决什么问题**：现在完全看不到"用了多少空间、还有多少余量"。你是靠我手动跑 SQL 才知道
"14 个包 1478MB"。没有这个，管理员无法判断何时该清理。

**动作**：新增 3 个接口（仅 `platform_admin`）：

| 接口 | 解决什么 |
| --- | --- |
| `GET /platform/storage/usage` | 总用量、预算余量、按 (项目,环境,平台) 分组分布、待同步数、失败数 |
| `POST /platform/storage/pin` | 固定/取消固定某包（写 `pin_kind`） |
| `POST /platform/storage/prune` | 手动触发一次淘汰，返回将删除的列表（不直接执行） |

**验证**：`curl` 拿到用量 JSON，数值与 SQL 统计一致。

**❓ 待确认**：Q6（是否需要"预估还能传几个包"）

**解决什么问题**：接口有了但管理员看不到。需要可视化才能判断"该清理了"。

## 需要你回答的问题

### Q1. 66 的计数范围
现在设计：按 `(项目 + 环境 + 平台)` 分组，各自 66 个。
即"项目A/test/android 有 66 个" 和 "项目A/prd/android 另有 66 个"。
**你的意思是这个，还是"一个项目总共 66 个（跨环境合并）"？**

### Q2. 9GB 预算的归属 ⚠️ 最关键
- **方案 A（我推荐）**：全局共享 9GB。所有租户用量相加不超 9GB，绝不超免费额度。
- **方案 B**：每个租户独立 9GB。多租户时会超免费额度（3 个租户就 27GB），需付费。

**你选哪个？** 选 B 意味着接受付费或超额风险。

### Q3. 淘汰是否通知上传者
现在设计：只写审计日志，不通知。
**要不要发飞书卡片告诉上传者"你的旧版本 X 已被清理"？**

### Q4. 巡检间隔
现在设计：每小时一次。
**够用吗？** 更频繁（如 10 分钟）能更快收敛，但会增加数据库负担。

### Q5. 孤儿对象怎么处理
R2 上有 2 个孤儿对象（238MB），数据库无记录。
**Worker 发现"有对象无记录"时：**
- (a) 自动删除 —— 省事，但万一数据库恢复备份，对象已被误删
- (b) 只在管理端列出，等你手动确认 —— 安全但需人工

### Q6. 是否需要"还能传几个包"预估
按当前平均包大小算 `(9GB - 已用) / 平均大小`。
**这个数字对你有用吗？** 有用我就在 UI 上显示。

### Q7. 管理端页面放哪个菜单
现有菜单是"概览 / 应用包 / 应用 / 人员管理 / 团队管理 / ..."。
**存储管理应该：**
- (a) 新增独立菜单项"存储管理"
- (b) 挂在现有"设置"下作为子页
- (c) 挂在"概览"里作为一块区域

### Q8. `pin_kind` 需要几种语义
- (a) 只要 `manual`（人工钉住，永不淘汰）—— 最简单
- (b) 保留 `manual` + `release`（重要版本，可配不同策略）—— 更灵活但当前用不上

### Q9. `last_accessed_at` 是否值得
每次下载都多一次 UPDATE 写入。
- (a) 要，淘汰时优先删"没人下载的旧包"，更符合实际价值
- (b) 不要，只按 `created_at` 淘汰，少一次写入

### Q10. 现有 2 个孤儿对象现在删吗
`direct/689a0049...`（119MB）、`direct/a6417236...`（119MB），早期失败上传的残留。
**现在就删掉，还是等 Worker 做好后统一处理？**

## 建议执行顺序

| 顺序 | 任务 | 理由 |
| --- | --- | --- |
| 1 | 任务 1（修 Delete 泄漏） | 独立、风险低、立刻止漏 |
| 2 | 任务 2（7 个字段） | 后续所有任务的数据基础 |
| 3 | 任务 3（淘汰算法） | 纯函数，可离线单测 |
| 4 | 任务 4 + 5（执行 + Worker） | 后端闭环，此时已能自动治理 |
| 5 | 任务 6 + 7（接口 + UI） | 可观察性与人工干预 |

做完 1—5 即实现自动治理；6—7 只是让你能看到和干预。
