### 0.1 原始需求复述（完整，不遗漏）

用户想做一个**类似于蒲公英（pgyer.com）的 Web 端软件**，要求：

1. 一份**前后端总体设计方案**：包含整体框架设计 + 功能页面设计，要方便后续扩展（由架构师与工程师承接）。
2. 支持不同**环境**上传 App 包：`test` / `hotfix` / `pre` / `prd` 四种环境。
3. 能够展示不同环境上传的包，包列表支持 **Android（.apk）和 iOS（.ipa）** 两种平台。
4. 支持点击包进入**独立下载页面**下载（类似蒲公英的下载单页）。
5. **第一版最小范围（用户已明确）**：① 软件内正常上传 App 包的接口；② 上传后按不同环境查询 App 包列表的接口（区分 android / ios）；③ 点击去独立页面下载包。
6. 需要参考蒲公英目前的功能，**把基础常用功能逐条列举出来，形成一张「功能清单 + 是否建议第一版实现」的决策表**，让用户自己决定第一版范围（本次交付重点）。
7. 用户另问：前后端代码是否放一起？后续如何部署？（由架构师回答，本文只列入待确认问题）
8. 用户强调：代码要简单优雅、结构清晰、遵循单一职责等设计原则、不冗余、注释完善、开发者一看就懂。

## 1. 产品目标与定位

这是一个**团队内部自建的多环境 App 包分发平台**，不是要复刻蒲公英的商业化能力。蒲公英面向「对外分发 / 客户验收 / 智能硬件配套 / 全球 CDN」，而本平台只解决一件事：**让团队内部的安装包按环境被准确地传上去、找得到、装得下**。因此第一版刻意砍掉账号体系、安装控制、统计报表、渠道、SDK 类能力，把复杂度留给「环境」这个维度。

与蒲公英最大的差异是：**「环境」在本平台是一等公民维度**。蒲公英的版本只有 Dev / Pro 两档标签（且属于账户增值能力）、按 `appKey` 聚合版本；本平台则以 `环境 × 平台` 作为列表与查询的第一入口，避免 test 包与 prd 包混淆——这是本平台存在的理由。

### 1.1 Product Goals（3 个正交目标）

| 编号 | 目标 | 可衡量标准 |
| --- | --- | --- |
| G1 上传效率 | 开发者无需培训即可把一个包传到指定环境 | 上传一个包在页面上的操作不超过 4 步（选文件、选环境、选平台、提交），1 分钟内完成 |
| G2 定位确定性 | 找包的人零歧义定位到目标包 | 任一包都可通过「环境 + 平台」两个条件在列表首屏找到；列表字段足以判断是不是要的包 |
| G3 可扩展基座 | 第一版代码与信息结构能承接后续能力 | 后续新增二维码 / 统计 / 安装控制 / 鉴权时，不改动上传与查询的主流程（期望，由架构师落地） |

## 2. 核心概念与术语表

| 术语 | 定义 | 取值 / 规则 |
| --- | --- | --- |
| 环境 Environment | 包所属的发布阶段，**本平台一等公民维度** | 固定四值：`test`（测试）、`hotfix`（紧急修复）、`pre`（预发）、`prd`（生产）。上传时必选，查询时为主条件 |
| 平台 Platform | 包运行的操作系统 | `android`（.apk） / `ios`（.ipa）。上传时必选或由文件类型推断，查询时为筛选条件 |
| 应用 App | 逻辑上的一款应用（如「商城 App」） | 第一版不要求独立管理 App 实体，以「应用名」字段体现即可（见 Q8） |
| 包 / 版本 Build | 一次上传产生的单个安装包及其描述信息 | 由「环境 + 平台 + 应用名 + 版本号 / 构建号 + 上传时间」唯一区分；同一环境同平台允许存在多个历史包 |
| 下载页 Download Page | 每个包对应一个独立的可访问页面 | 上传成功后生成；展示包信息并提供下载入口；地址可被复制或转发给他人 |
| 包的元数据 | 列表页与下载页需要展示的描述信息 | 应用名、平台、环境、版本号、构建号、文件大小、上传时间、更新说明；第一版可由上传表单填写（见 Q4） |
| 上传者 / 访问者 | 内部开发者；内部测试 / 产品 / 项目负责人 | 第一版默认不做身份区分（见 Q3） |

> **口径提醒**：本文中的「接口」指产品能力层面的输入与输出约定，不涉及 HTTP 方法、字段类型、状态码等技术定义，具体契约由架构师设计。

## 4. 功能页面设计

### 4.1 页面清单

| 页面 ID | 页面 | 目标 | 优先级 | 对应需求 |
| --- | --- | --- | --- | --- |
| P-01 | 上传页 | 把包与「环境 / 平台 / 描述信息」一起提交 | P0 | 用户明确 ① |
| P-02 | 应用 / 包列表页 | 以环境与平台为入口找到包 | P0 | 用户明确 ②③ |
| P-03 | 独立下载页 | 核对信息并下载安装包 | P0 | 用户明确 ④③ |
| P-04 | 应用概述 / 统计看板 | 跨环境总览 | P2 | 后续演进 |
| P-05 | 管理设置页（成员 / 渠道 / 密码等） | 后台配置 | P2 | 后续演进 |

> 第一版只有 P-01 / P-02 / P-03 三个页面，页面之间跳转关系极简：上传成功 → 下载页；列表 → 下载页；各页可互相返回。

### 4.2 页面区块、元素与交互

#### P-01 上传页

| 区块 | 元素 | 交互 / 规则 |
| --- | --- | --- |
| 顶部导航 | 产品名、跳「包列表」入口 | 全站统一，保持极简 |
| ① 文件选择区 | 拖拽区 / 点击选择按钮、已选文件名与大小、移除按钮 | 仅接受 `.apk` / `.ipa`；选中后在界面上回显文件名与大小；类型不符给出明确提示 |
| ② 必填信息 | 环境（test / hotfix / pre / prd 四选一）、平台（Android / iOS 二选一） | 环境必选、无默认值或默认 `test`（见 Q9）；平台可根据扩展名自动带出，仍允许人工修正 |
| ③ 选填信息 | 应用名、版本号 / 构建号、更新说明 | 第一版由上传者填写；为空时列表与下载页用文件名 / 占位值兜底，不阻塞上传 |
| ④ 提交与反馈 | 「上传并发布」按钮、进度反馈、成功卡片 | 提交中禁用重复提交；失败给出可读原因；**成功后展示该包下载页地址 + 「去下载页」按钮 + 「返回列表」**，并支持复制地址 |
| 通用 | 空态 / 错误态 / 校验提示 | 必填缺失、文件过大、上传失败均有文案反馈（属上传能力的内含质量，非新增功能） |

#### P-02 应用 / 包列表页

| 区块 | 元素 | 交互 / 规则 |
| --- | --- | --- |
| 顶部 | 产品名、「+ 上传包」按钮 | 直达 P-01 |
| 一级：环境切换 | `test` / `hotfix` / `pre` / `prd` 四个切换项 | 单选、当前项高亮；切换即按新环境重新拉取列表；**环境是页面的主维度，始终可见** |
| 二级：平台筛选 | 全部 / Android / iOS | 单选；与 environments 组合生效 |
| 包列表 | 每行：平台标识、应用名、版本号（含构建号）、文件大小、上传时间、更新说明摘要、操作「下载页」 | 按上传时间倒序；同一环境同平台展示多个历史包；点击行或「下载页」进入 P-03 |
| 空状态 | 「当前环境暂无包」+「去上传」 | 无数据时不得显示空白表格 |
| 通用 | 加载态、错误态、包数量提示 | 查询失败给出可读提示 |

#### P-03 独立下载页

| 区块 | 元素 | 交互 / 规则 |
| --- | --- | --- |
| 头部 | 产品名 / 应用图标占位 | 手机浏览器优先布局，单列居中 |
| 包信息区 | 应用名、**环境标签**、平台标签、版本号（含构建号）、文件大小、更新时间、更新说明 | 信息必须足以让用户确认「是不是要装的包」；**环境标签是本平台下载页区别于蒲公英的必显字段** |
| 主操作 | 「下载 / 安装 App」按钮 | 点击取得原始 `.apk` / `.ipa` 文件；iOS 能否在浏览器直接安装见 Q5 |
| 辅助 | 复制下载页地址、返回包列表 | 便于转发给同事 |
| 预留位 | 二维码占位（P1，见 D1） | 第一版可留空或不展示，不为它增加前后端逻辑 |

### 4.4 关键流程

- **流程 A · 上传**：进入 P-01 → 选文件 → 选环境（必填）+ 平台（必填）→ 填选填项 → 提交 → 服务端保存包文件与元数据 → 返回包标识与下载页地址 → 页面展示成功卡片。
- **流程 B · 找包下载**：进入 P-02 → 切环境 → 筛平台 → 定位目标包 → 点「下载页」→ P-03 核对信息 → 点下载按钮 → 取得原始安装包。
- **流程 C · 扫码（P1）**：扫二维码 → 打开 P-03 → 同流程 B 末段。
- **第一版端到端验收标准（建议）**：上传一个约 30 MB 的 `.apk` 并选择 `hotfix` + Android → 切到 `hotfix` 环境并筛选 Android → 列表出现该包（信息与上传时一致、时间倒序）→ 点击进入独立下载页 → 点击下载得到与上传内容一致的文件；切换到 `test` 环境时该包不出现。

## 5. 需求池（P0 / P1 / P2）

> **P0 严格对应用户已明确的第一版最小范围，不擅自扩大。** 表内 P0 项均为三项最小范围或其内含属性，未引入登录、二维码、统计等新功能。

### P0 · Must have（第一版，用户已明确）

| 编号 | 需求 | 描述 | 验收标准 | 来源 |
| --- | --- | --- | --- | --- |
| P0-1 | 上传页 | Web 端可选 / 拖入 `.apk`、`.ipa`，必填环境与平台，选填应用名 / 版本号 / 更新说明 | 见 P-01；提交成功后可见下载页地址 | 最小范围 ① |
| P0-2 | 上传接口 | 接收包文件 + 环境 + 平台 + 元数据，持久保存并生成该包的下载页地址 | 上传成功后文件不因服务重启丢失；返回可访问地址 | 最小范围 ① |
| P0-3 | 按环境 / 平台查询包列表接口 | 查询条件：环境（必选）、平台（可选）；返回该条件下包列表，每条含平台、应用名、版本号、大小、上传时间、更新说明、下载页地址 | 按上传时间倒序；切环境后结果只包含该环境包 | 最小范围 ② |
| P0-4 | 包列表页 | 环境四值切换 + 平台筛选（全部 / Android / iOS），列表展示上述字段 | 见 P-02 与端到端验收标准 | 最小范围 ②③ |
| P0-5 | 独立下载页 | 每个包一个独立地址，展示应用名、环境、平台、版本号、大小、更新时间、更新说明与下载按钮 | 地址可复制转发；手机浏览器可正常打开 | 最小范围 ③ |
| P0-6 | 下载接口 | 点击按钮可取得该包的原始 `.apk` / `.ipa` 文件 | 下载文件与上传文件一致；iOS 直接安装方式见 Q5 | 最小范围 ③ |
| P0-7 | 基础校验与反馈 | 文件类型 / 大小、必填项、上传失败与空状态提示 | 每种异常均有可读文案，不出现空白页 | P0-1 / P0-2 的内含质量要求，非新增功能 |

### P1 · Should have（第二版候选，可按需勾选并入第一版）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| P1-1 | 下载二维码（下载页 + 列表） | 解决用户提到的「手机扫码」场景，成本低、感知强 |
| P1-2 | 包元数据自动解析 | 自动读取应用名 / 版本号 / 构建号 / Bundle ID / Package ID / 图标 / 大小，减少手填 |
| P1-3 | 下载次数 | 每个包记录下载次数并在列表 / 下载页展示 |

### 6.1 主理人建议的第一版组合（可直接勾选）

- ☐ **必选（P0，用户已明确，不建议删减）**：上传页 + 上传接口 + 按环境 / 平台查询列表接口 + 包列表页（四环境切换 + 平台筛选）+ 独立下载页 + 下载接口。
