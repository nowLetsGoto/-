# 05 · 板块路线图（增量产品文档）

> 作者：许清楚（产品经理）｜日期：2026-11-13｜基线：`01-PRD.md` + `04-DELTA-PRD.md`｜效力：只描述多板块结构性预留，冲突处以本文为准，未提及部分沿用基线；**不改变第一版范围**。
> 纪律：一级导航技术结构、路由、数据库框架与 DDL **由架构师定稿**；本文不做技术选型、不写代码、不与架构师或工程师直接通信。

## 1. 定位变化

**一句话**：本平台从「多环境 App 包分发工具」升级为「**多板块内部研发交付平台**」——应用包分发是第一个已落地板块，pushy 类热更新包与其他研发功能为后续板块。此定位变化**不改变第一版 P0 范围**，仍以 01-PRD + 04-DELTA-PRD 的 **10 条 P0** 为准，也不新增任何第一版功能。

## 2. 未来板块清单

| 板块名称 | 一句话职责 | 典型页面（仅列名，不展开） | 与主板块共享的概念 | 预计优先级 |
| --- | --- | --- | --- | --- |
| 应用包分发（当前主板块，第一版已实现） | 四环境上传 / 查询 / 独立下载页分发 .apk 与 .ipa | 上传页、应用包列表页、独立下载页 | 应用、环境、平台、版本 / 构建号、包文件、时间、分发地址、下载次数 | P0（现行） |
| 热更新包（pushy 类，未来板块） | 上传与管理热更新包，按应用与基线原生版本发布、灰度、回滚 | 热更新包列表页、发布配置页、灰度与回滚页、版本兼容视图 | 应用、环境（取值待确认）、平台、版本 / 构建号、上传时间、分发地址 | P1（未来，待确认） |
| 成员与权限（其他功能候选） | 管理谁可上传、发布、查看 | 成员列表、角色配置 | 应用、环境 | P2（候选） |
| 发布统计看板（其他功能候选） | 跨板块查看发布与下载趋势 | 概览看板、下载明细 | 应用、环境、平台、版本、时间 | P2（候选） |
| 发布通知配置（其他功能候选） | 配置新包 / 新热更新发布后的通知对象与渠道 | 通知规则、渠道配置 | 应用、环境、上传时间点 | P2（候选） |

**pushy 类热更新平台核心对象与操作**（联网核实，仅用于板块页面命名，**非第一版需求**）

| 核心对象 / 操作 | 含义 |
| --- | --- |
| 应用（appKey，按平台分别创建） | 热更新归属主体，含应用名与安装包下载地址 |
| 原生基础包 / 基线版本（packageId / packageVersion） | 每个原生版本上传一次，作为差量计算基准 |
| 热更新版本（ppk / bundle，含名称、描述、metaInfo） | 实际下发的 JS / 资源更新包 |
| 版本绑定（原生包版本 ↔ 热更新版本） | 可绑定单版本或最低 / 最高 / semver 范围，决定兼容性 |
| 灰度 rollout（1–100%）与全量发布 | 同一原生包可同时存在灰度与全量版本 |
| 回滚 / 自动崩溃回滚、差量更新、CDN 分发、CLI + 网页管理、客户端 checkUpdate | 发布后的恢复、分发与检测链路 |

> 来源（2026-11-13 检索）：`https://pushy.reactnative.cn/`、`https://pushy.reactnative.cn/docs/migrate-from-codepush`、`https://v9--pushy-site.netlify.app/docs/cli`、`https://github.com/yuanwy/react-native-pushy/blob/48b70f3bf48bd8e04513311a42a643d9d3484f39/docs/cli.md`。口径：Pushy 无 CodePush 的 Staging/Production 部署概念，测试用扫码 / Deep Link、线上用灰度控制范围；「环境」是否复用本平台四值见 Q3。已排除同名不同产品的 `pushy.me`（推送通知服务）；本文「pushy 热更新板块」与 04 §3「push 通知平台预留」是两件事。

## 3. 页面位置与导航关系（产品口径）

| 区域 | 第一版（现在） | 未来（示意，非第一版范围） |
| --- | --- | --- |
| 品牌区 | Dandelion 产品名，全站固定 | 不变 |
| 一级主导航 | **仅「应用包」一个真实入口** | 应用包 / 热更新包 / 其他板块，平级并列 |
| 内容区 | 上传页、包列表页、独立下载页 | 各板块自己的页面集合，随主导航切换 |

```
现在：  Dandelion ── [应用包]   ── 上传 / 包列表 / 下载页
未来：  Dandelion ── [应用包]   ── 上传 / 包列表 / 下载页
                ├─ [热更新包] ── 包列表 / 发布 / 灰度 / 回滚
                └─ [其他板块] ── 成员与权限 / 统计看板 / 通知配置
```

**第一版不放「热更新 敬请期待」这类禁用占位菜单、不建空页面、不加隐藏入口、不做板块开关**；预留体现在一级导航的位置关系与共享概念的结构清晰度上，不靠占位代码。

## 4. 跨板块共享概念（给架构师数据库框架的产品依据）

| 概念 | 归属 | 为什么未来要能被多个板块引用 |
| --- | --- | --- |
| 应用 App | 跨板块共享 | 热更新包必须挂到某个应用；统计、权限、通知也以应用为聚合单位；第一版以「应用名」体现，未来需成为可被引用的稳定主体 |
| 环境 test / hotfix / pre / prd | 跨板块共享（取值待确认） | 热更新发布同样分阶段；Pushy 类平台无 Deployment 概念、以灰度控制范围，是否复用四值见 Q3 |
| 平台 android / ios | 跨板块共享 | 热更新包同样按端构建与下发；权限、统计按端筛选 |
| 版本 / 构建号 | 跨板块共享 | 热更新包需绑定兼容的基线原生版本，是发布、灰度与回滚的依据 |
| 包文件 | 板块特有 | 应用包是 .apk/.ipa，热更新包是 ppk/bundle/差量包，形态不同；但「上传—持久化—可访问地址」链路应一致 |
| 上传 / 发布时间 | 跨板块共享 | 各板块列表排序、统计时间轴与通知触发时点的共同依据（对应 04 §3.2 R4） |
| 下载 / 分发地址 | 跨板块共享 | 应用包是下载页绝对地址 + 二维码，热更新包是客户端拉取地址；都要求稳定、可引用 |
| 下载次数 | 板块特有 | 目前只服务应用包分发；热更新板块更关注覆盖率 / 活跃设备数，口径不同，不宜强行复用 |

> 产品侧只要求「共享概念作为平台级稳定主体、不因新增板块被复制或改名」，板块特有概念由各板块自行扩展；**具体数据模型、字段与数据库框架由架构师定稿**。

## 5. 第一版边界（负面清单）

- 不实现热更新包上传 / 管理 / 发布 / 灰度 / 回滚 / 版本绑定 / 差量包，不实现任何其他板块功能。
- 不新增板块相关表单字段、页面、菜单项、空页面或隐藏入口；不做板块开关、插件、模块配置、板块级权限。
- 第一版只保证「后续能加得进来」：一级导航有明确定位关系、共享概念不固化在单一板块内；除此之外不写任何为多板块而写的代码。
