### 踩坑（重要）
1. `INSERT ... SELECT $1, id` 里纯常量投影参数 PG 无法推断类型 → 必须写 `$1::uuid`。

### 缺陷1：角色分配可提权
- 实测确认：团队管理员给人员设 roleKey=super-admin → 该人员建账号获得全量10项权限。
- 根因：service/people 完全不校验 roleKey（我 P3 的 handler 注释写"由 service 校验"是假的）。
- 修复：authz.ValidateRoleAssignable 唯一判定点 = 可见性(内置或本公司) + 权限不超出调用者。挂在 people.Service 的 Create/Update，用 RoleAssigner 窄接口。
- 验证 7/7：团队/平台管理员分配 super-admin 均400、developer 允许、不存在角色400、编辑时也拦。

### 缺陷2：API Key 明文存储
- 修复：库存 SHA-256 摘要，明文只在轮换响应出现一次；GET /settings 改返回 apiKeyConfigured(bool)。
- **迁移关键**：schema.sql 就地哈希化（判据 length<>64 幂等），旧 Key 继续可用（调方发明文，服务端算摘要比对）。实测旧 Key 201、拿摘要当Key 401。
- 新公司首次建行 api_key 留空=未生成（自动生成却没明文交付路径，填给用户必 401），让管理员主动轮换。
- 选 SHA-256 非 bcrypt：Key 是 128 位随机串无弱口令问题，上传是热路径慢哈希会拖延迟。

### 缺陷3：无登录限流
- 新增 service/login/ratelimit.go，按「账号+IP」双维度：5次失败锁15分钟，成功清零。
- 只按账号会被用来锁死别人账号(DoS)，只按IP换代理即绕过，故取交集。
- 不存在账号同样计数并锁定（否则可枚举真实账号）。返回 429 明确告知（不泄漏存在性，且避免真实用户反复重试续锁）。
- 单实例内存实现，多实例需换 Redis（注释已写明）。进程重启清零（刻意）。
- 验证：前5次400、第6次起429、锁定期间正确密码也429、换IP正常200。单测6项。

## P1-#4 跨公司重名支持（唯一约束租户化，已完成）

选它做第一个 P1 的理由：不需要特殊条件，第二家真实公司入驻就撞墙（zhangsan / mall 这类名字遍地都是）。

### 关键判断
- **users.username 保持全局唯一**：它是登录标识，登录只按这一个字段查，改租户内唯一会随机登录进别人账号。
- 只改 people.username 和 team.projects.key 为 (coalesce(tenant_id,零UUID), 字段) 部分唯一。

### 两个迁移坑（都已修）
1. 新索引依赖 tenant_id 列，但该列在 schema.sql 后半段才 ALTER ADD —— 写在原位置启动即报 column does not exist。移到加列之后。
2. projects_key_key 在老库是唯一**约束**(contype='u')不是索引，DROP INDEX 无效，必须 ALTER TABLE DROP CONSTRAINT。两种形态都写。

### 连带修复（比唯一约束本身更危险）
authz.PersonID 兜底用 Scope{All:true} 按 username 找档案。people.username 改公司内唯一后会随机命中别家同名人员，而 PersonID 参与 scope 推导 → 成员按别人算 team_ids → 看到别家团队数据。
改为 Scope{TenantID: identity.TenantID}。超管 TenantID 空，ApplyTenant 追加 1=0 失败关闭（正确，超管本无业务档案）。

### 验证 15 项
