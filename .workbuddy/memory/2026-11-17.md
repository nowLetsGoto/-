# 2026-11-17（下午）前端：单人模式「零项目」引导修复

## 用户问题
截图现场：单人模式普通用户（zouliang）访问 `/p/web/packages`，页面显示红色 `488 项目不存在，请刷新项目列表后重试`，而不是像 admin 那样给「去创建项目」的引导。

## 根因
不是「空包状态」问题，是**项目守卫漏判**。`web/src/hooks/useProjects.ts` 里：
```ts
const notFound = !loading && projects.length > 0 && project === null;  // 旧
```
`projects.length > 0` 这个前置条件让「一个项目都没有」时 `notFound=false`，守卫放行，
页面带着地址栏里的废 key 去请求 `/builds`，后端只能回 488。

## 改动（3 个文件）
1. `web/src/hooks/useProjects.ts`
   - `CurrentProject` 新增 `empty: boolean`
   - `notFound` 去掉 `projects.length > 0`：`const notFound = !loading && project === null;`
   - `const empty = notFound && projects.length === 0;`
   - 关键：`empty` 把「零项目」与「key 失效」两种成因分开，因为二者该给的引导不同
2. `web/src/components/ProjectGate.tsx` 按单一职责拆分
   - `ProjectScopedGate`：只做事实判定 + 分流（`empty ? <NoProjectYet/> : <ProjectMissing/>`）
   - 新增并导出 `NoProjectYet`：零项目 → 唯一动作「新建项目」，链接 `/directory/projects/new`
   - `ProjectMissing`：key 失效 → 「回到最近项目」+「去项目管理」；内部加 `if (!fallback) return <NoProjectYet/>` 兜底（同时满足 TS 收窄）
3. `web/src/App.tsx`
   - `ProjectHome` 的零项目分支改复用 `<NoProjectYet/>`，删掉各写一套的 `<Empty>`，文案不再两处不一致

## 权限前提（已验证，不是猜测）
- `server/internal/service/authz/service.go` 的 `soloPermissions()` 含 `project.write` → 单人普通用户可自建项目
- `web/src/components/navigation.ts` + `Sidebar.tsx` 的 `soloAllowed` 含 `/directory/projects` → 菜单可达
- `ProjectFormPage` 的 `solo` 分支不请求角色列表 → 单人建项目不会因 `role.read` 缺权而崩

# 2026-11-17（晚）四项需求：模式列 / tab 换库 / 删除账号 / 侧栏账号卡 + 改密

## 需求与落点

| 需求 | 落点 |
|---|---|
| 审计日志加「模式」列 | 后端 `contract.AuditLog.Mode` + `Partition.Mode()` + 仓储回填；前端表格插列与抽屉补行 |
| tab 换组件库并修垂直居中 | 五处手写 tab 全换 `Controls.Segmented`；删掉 `.segment*` / `.env-*` 两组死样式 |

| 侧栏头像弹层（模式 / 改密 / 退出） | 新组件 `AccountMenu`（Popover 向上弹）+ `ChangePasswordDialog` + `PUT /me/password` |

## 关键技术判断（都是验证过的，不是推测）

- **「模式」列零迁移**：`solo.audit_logs` / `team.audit_logs` 是按模式物理分区的，分区身份本身就是模式。加 `Partition.Mode()` 逆映射后由仓储在循环外算一次 `mode` 再回填，不用加列、不用改 DDL、不用回填历史。
- **垂直居中根因**：`styles.scss` 里 `.segment { display: inline-flex; align-items: baseline; }` —— `baseline` 就是「字体没有垂直居中」的直接原因。换库时把这一整组死样式删掉，问题随根因一起消失，不需要再叠 `line-height` 补丁。
- **删除账号无级联障碍**：`projects` / `builds.owner_user_id` 都是 `TEXT` 非 FK，`users` 表唯一外键是 `person_id → people(id) ON DELETE SET NULL`，所以 `DELETE FROM users` 不会被挡，历史构建与审计日志也不丢（`actorName` 是冗余存储）。
- **改密必然踢下线**：`SetPassword` 一定自增 `token_version`，旧令牌当场失效。产品决策定为「改密成功即清会话回登录页」，而不是换发新令牌把用户留在原地——后者要在失效瞬间做令牌轮换，复杂且收益为零。
- **antd 会在两个中文字之间插空格**：`okText="删除"` 渲染出的 DOM 文本是「删 除」，Playwright `has-text("删除")` 匹配不到。自动化里确认按钮一律按 `.ant-modal .ant-btn-primary` 定位。
- **`Popover` 的 `overlayStyle` 不生效**（类型可疑且实测无效），宽度改由 `.account-card { width: 240px }` 决定。

# 2026-11-17（晚）账号编辑 + 角色可设 + 模式只读

## 需求
1. 超管在账号管理里能编辑每个账号，并能给账号设角色。
2. 模式随登录固定，账号表单里**不应让用户切换**，只读展示。

## 设计决策（关键）
- **模式来源**：`LoginInput.mode` → `NormalizeMode("")→solo` → 令牌载荷 `username|token_version|exp|mode` → `contract.Identity.Mode`。建账号不再从请求体取 mode，改用 **`caller.Mode`**（handler 从 `authctx.From(ctx)` 取）。`UserInput` **删除 mode 字段**，`DecodeJSON` 白名单同步去掉它——请求体带 mode 直接 400。
- **角色归属**（经 AskUserQuestion 确认）：写到**绑定人员的档案** `people.role_key`，**不给 users 加 role_key**。理由：真相来源唯一，账号页改角色 == 人员管理改角色。`User.roleKey/roleName` 是两次 `LEFT JOIN`（users→people→roles）的**展示投影**，不是列。
- **新建不能设角色**：账号还没绑人员，没有地方落值。故 `roleKey` 只在 `UserUpdate` 里，`UserInput` 没有；前端未绑人员时角色下拉置灰。

## 顺带修掉的真 bug（上一轮遗留）
删除 team 账号后，它在 solo 分区的项目成永久孤儿。根因：`Delete` 里 `if current.User.Mode == ModeSolo` 判断过窄，而 `login.Service.Authenticate` **完全不校验 users.mode**——team 账号照样能以 solo 模式登录并产出 solo 数据。
→ 改成**无条件 `PurgeSoloData`**，判定依据只能是「该 id 在 solo 分区有没有数据」。多清一次是空转（两条 DELETE），少清一次就是永久孤儿。
端到端复验：team 账号 roletest 以 solo 模式建项目 `sololeak` → 从 team 视角删账号 → solo.projects/builds 均 0。

## 改动文件
- `contract.go`：`UserInput` 去 mode；`User` 加 `RoleKey/RoleName`；`UserUpdate` 加 `RoleKey`；`NormalizeAccountMode` 注释限定为「种子账号等无登录上下文的内部调用」
- `repository/user/repository.go`：`fromClause` 两次 LEFT JOIN；`Update` 改**事务**同时写 `users.person_id/is_super_admin` + `people.role_key`；`scanRecord` 多扫两列
- `service/user/service.go`：`Create(ctx, caller, in)`；`Update` 加跨模式护栏（≠caller.Mode → errAccountNotFound）+ 透传 roleKey；新增 `Get`；`Delete` 无条件清理
- `handler/user/handler.go`：白名单 "username/password/personId/isSuperAdmin" 与 "personId/roleKey/isSuperAdmin"；新增 `Get`；审计 detail 加 roleKey
- `app/router.go`：`admin.Get("/admin/users/{id}")`
- `api/openapi.yaml` + `make gen:api`
- 前端：`api/users.ts` 加 `getUser`；`AccountFormPage.tsx` 整文件重写（new/edit 双用途、模式只读、角色下拉）；`AccountsPage.tsx` 加角色列 + 编辑入口；`App.tsx` 加 `/admin/accounts/:id/edit`；`styles.scss` 加 `.readonly-value`
- `AGENTS.md`：第 160/161/166 行三处过时表述重写（建账号默认 team 那条整条删除，因为已无 mode 入参）

# 团队模式：角色管理收归超管

## 需求
「团队模式中：只有超级管理员可以对角色管理进行操作。」

## 设计决策
- **角色管理不是权限点**：既然只对超管开放，`role.read` / `role.write` 留着就是"勾了也没用"的无效选项（经 AskUserQuestion 确认两个一并删除）。改由三层同构的"超管专属"判定：`NavItem.requireSuperAdmin`（菜单）→ `AdminGate`（整页）→ `RequireSuperAdmin`（接口）。
- **五个接口**（`/permissions`、`/roles` 列表/详情/新建/编辑）留在 `admin` 组内，仍叠 `RequireTeamMode`——单人空间没有角色概念。
- **顺带修权限倒挂**：`defaultPermissions()` 含 `directory.read`（普通成员能看内部通讯录），而内置 `guest` 没有它 ⇒ 分配了 guest 反而比"没有角色"少看一个菜单。三个业务角色统一补齐 `directory.read`，写入（`directory.write`）仍只给 project-owner。

## 改动文件
- `contract.go`：删 `role.read` / `role.write` 两条目录项
- `service/authz/service.go`：`defaultPermissions()` 加 `directory.read`
- `service/role/service.go`：内置角色全删 `role.read`；`guest` 补 `directory.read`
- `repository/schema.sql`：幂等 `DELETE FROM role_permissions WHERE permission IN ('role.read','role.write')` + 对内置 guest 幂等 `INSERT ... ON CONFLICT DO NOTHING`
- `app/router.go`：注释措辞修正（五个接口）
- `handler/role/handler.go`：包注释改为「整块接口仅超管可用」
- `api/openapi.yaml`：`/permissions` GET、`/roles` GET、`/roles/{key}` GET 补 403 并标「仅超级管理员」
- 前端：`navigation.ts` 加 `NavItem.requireSuperAdmin`；`Sidebar.tsx` `canSee` 优先判它；`App.tsx` 三条角色路由 `PermissionGate` → `AdminGate`（列表页原本无守卫，一并补上）；`RolesPage.tsx` 删掉冗余的 `me?.isSuperAdmin` 判断（AdminGate 已保证）；`ProjectFormPage.tsx` `showRoleField = !solo && me?.isSuperAdmin === true`
- `service/authz/service_test.go`：清掉恒真的 `role.write` 断言，补 `role.*` 不存在的正向断言
- `AGENTS.md`：主数据段加角色归属说明、默认基线改含 `directory.read`、新增「超管专属用 requireSuperAdmin/AdminGate」一条、操作索引加一行

## 门禁 + 实测
四道全绿（go build/vet/test、tsc、eslint+stylelint、make build）。端到端：
- 超管 `/me` 10 项权限无 `role.*`；`GET /roles`、`/permissions`、`/roles/super-admin` 均 200
- 普通账号（guest）`/me` = `build.read, directory.read, project.read`；五个角色接口全部 403（含 POST/PUT）
- 普通账号人员/团队/项目 GET 均 200；`POST /people`、把自己改成 super-admin 的 PUT 均 403
- 换成 project-owner 后 `POST /people` 201，但 `GET /roles` 仍 403 ⇒ 写能力与角色可见性已解耦

## 坑
- **`schema.sql` 内嵌二进制**：`//go:embed` + `EnsureSchema` 只在启动跑一次，改完 SQL 必须重新 `go build` 再重启，否则跑的是旧 DDL（本轮踩过一次）。
- **`EnsureBuiltin` 只插不改**：`CreateBuiltinIfMissing` 在 key 存在时直接跳过，改内置角色权限对存量库无效，必须靠幂等 SQL 补。
- **`role_permissions.permission` 是裸 TEXT 无外键**：删目录项不会自动清库，必须显式 DELETE。
- 菜单若继续用已删权限点判定，会对所有人（含超管）恒 false，菜单整体消失——所以必须走 `requireSuperAdmin` 而非 `permission`。

## 数据清理
删掉本轮探针账号 `roleprobe` 及其两条人员档案（`权限探针`/`d86402fb…`、`探针新增`/`c2745210…`，删除前确认 project_members/team_members/users 均无引用）。`people` 表恢复到 linanan、zouliang 两条；`users` 仍 3 条（admin/zouliang/linanan）；`role_permissions` 中 `role.*` 计数为 0。
