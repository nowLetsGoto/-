## 后台服务 78 的真正根因（14:04 日志确认，已修复）

### 决定性日志
用户在终端 log show 抓到：
  Service could not initialize: posix_spawn(/bin/bash), error 0x1 - Operation not permitted
  xpcproxy exited due to exit(78)

### 根因
这台 Mac 的安全策略禁止 launchd spawn /bin/bash（即使 vite 的 bash 版本之前"看起来"成功，
server/tunnel 经 bash 启动必被拒）。不是 plist 语法、不是冷却期、不是命令本身——
验证：同样的命令在 env -i 最小环境下手动执行完全正常。

### 修复（关键教训）
plist 里**绝不要用 /bin/bash -lc 包裹**。改为：
- server: ProgramArguments 直接指向 bin/dandelion 绝对路径；
  环境变量通过 plist 的 EnvironmentVariables 字典内联（从 .env 生成，HTML 转义）。
- tunnel: ProgramArguments 直接指向 cloudflared 真实路径
  /opt/homebrew/Cellar/cloudflared/2026.11.2/bin/cloudflared（绕开 symlink）。
- 两个 plist 已确认 grep bash = 0 处，plutil 校验 OK。
- 内联环境变量直接执行二进制已验证能正常启动。

### 通用原则（写进长期记忆候选）
macOS launchd LaunchAgent 若报 EX_CONFIG(78) 且日志有 posix_spawn(...): Operation not permitted，
说明该可执行文件被系统策略禁止 spawn。解决：plist 直接列可执行文件路径 + EnvironmentVariables，
不要用 shell 包裹，不要用 symlink。

## Cloudflare R2 下载加速（已完成，17:51）

  Create 末尾触发 syncToR2Async

- `server/internal/handler/build_handler.go`：streamFile 优先 302 跳转

## 浏览器直传 R2（已完成，20:18）

### 解决的问题
Cloudflare Tunnel 免费版请求体上限 100MB → 300MB 包直接 413。
改成浏览器拿预签名 URL 直接 PUT R2，字节完全不经过本机和 Tunnel，
只受 R2 限制（单次 PUT 5GiB），**不需要分片**。

### 流程
1. POST /builds/upload-ticket → 返回 putUrl + Header + uploadToken
2. 前端 XHR PUT putUrl（直连 R2，带进度条）
3. POST /builds/stage-from-r2 → 校验大小 + 回拉本地 + 解析 → stageToken
4. POST /builds（原有 commit，不变；r2_key 直接指向 direct/ 对象，不二次上传）

### 新增文件
- server/internal/storage/r2.go：加 PresignPutURL / DownloadTo / StatObject / DeleteObject
- server/internal/repository/upload_session.go：upload_sessions 表仓储

- server/internal/handler/build_upload_handler.go：三个接口
- api/openapi.yaml：三个接口契约（契约测试强制同步）

### 关键设计
- **伴生 .r2 文件**：回拉时在 tmp 写 token.r2 记录 R2 对象名，commit 读到就跳过二次上传。
  validateStageToken 的循环要排除 .name 和 .r2，否则会被误判成扩展名。
- **自动回落**：未配 R2 时 /upload-ticket 返回 400「未启用对象存储」，
  前端据此静默回落 multipart；其余错误（网络/大小不符）必须提示用户。
- **ApiError 属性名是 `code` 不是 `status`**（我一开始写错了，tsc 拦下）。

## ✅ 下载文件名修复（2026-11-26 15:32，commit 874573a）

### 问题
用户截图：下载得到 `1d828823-a1a1-4f85-9712-65a603ced080.apk`（UUID），
而非上传的 `景田_正式环境_26.10.1.apk`。

### 根因
302 跳到 CDN 后，R2 对象本身没有 Content-Disposition 元数据，
浏览器只能用 URL 末段（UUID）当文件名。直传对象由浏览器 PUT 生成，
预签名里没设该头。

### 关键技术决策
预签名 PUT 里设置 Content-Disposition 会导致前端必须原样带该头
（和 Cache-Control 同理，参与签名），否则 403。为不改前端，改用：
- 普通上传：R2.Put 直接写入元数据（一次完成）
- 直传包：发布后 R2.SetContentDisposition 用 CopyObject 改写自身元数据
  （R2 内部复制不传字节，代价小）

### 顺序约束（重要）
必须先补元数据再预热 CDN。反过来会让不含文件名的响应头被 CDN
缓存一年（objectCacheControl = immutable），之后无法纠正。

### 代码
- storage.ContentDisposition：从 handler 提取为公共实现，
  本机流式与 R2 元数据共用 RFC 5987 编码
- R2.Put 加 fileName 参数
- R2.SetContentDisposition(ctx, key, fileName, contentType)

## ✅ 任务3 淘汰算法（2026-11-26 18:22，commit e78d973）

### 文件

### 设计
纯函数 PlanRetention(candidates) → RetentionPlan{Evict, Keep, TotalBytes}
不读库/不发网络/不删东西，调用方（Worker、上传前预检）共用同一份判定。

约束（同时生效，先到者为准）：
- retentionMaxVersions = 66（每租户）
- retentionMaxBytes = 9 GiB（每租户）

### ⚠️ 踩坑记录（重要）
第一版按"淘汰优先级"排序（最该淘汰在前），然后从队首逐个保留
→ 方向完全相反，把最该删的优先保留了。
测试暴露：Evict=[hot-old] Keep=[cold-new]。
修正：改成"保留优先级"排序（最近访问优先、从未下载排最后），
从队首保留到超限为止，剩下的全部淘汰。

- r2_bytes=0 不占预算（未同步/已淘汰的包）

## ✅ 任务4 淘汰执行器（2026-11-26 18:28，commit 42584b9）

### 文件
- repository/build_retention.go（SQL 层）

### 三步顺序不可交换
1. ListRetentionCandidates：只取 r2_key非空 且 r2_bytes>0
   （无对象名的不在桶里、字节0的已淘汰/未同步，都不占预算）
2. DeleteObject 逐个删，失败的跳过（一条删不掉不该让其余包继续占空间）

   - r2_key='' （关键：否则继续签发失效直链）
   - r2_bytes=0 （容量统计立刻释放）
   - r2_state='evicted'
   - r2_synced_at=NULL
   - **不删行**

### 自愈设计
标记失败时 r2_bytes 仍>0 → 下次巡检重试删除；
DeleteObject 对不存在对象视为成功 → 不会卡死。

### TouchAccessedAt
记录下载时间，供淘汰判断。失败不返回错误（不影响下载体验）。

### 实测验证
- 集成测试 2 个通过：MarkEvicted 保留行 + evicted 不再进候选
- 端到端：造真实 R2 对象+记录 → 淘汰 → 对象消失、三字段如预期、记录仍在
- 无测试残留对象
