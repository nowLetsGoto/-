### 关键架构决策
- **编辑不得绕过状态机（安全底线，四道闸门）**：①编辑 DTO（DevTaskUpdate/DevSubtaskNoteUpdate）无 status 字段 + DecodeJSON DisallowUnknownFields 递归拒任意层级 status；②仓储编辑 SQL SET 不含 status；③状态写入只走 /transition（DevNextStatus）与 /skip（CanSkipDevStatus）；④无 unskip 接口 → SKIPPED 永久不可恢复。一句话：编辑改"资料"，推进/跳过改"状态"，状态唯一写入口=状态机。
- 状态机 SSOT=openapi 的 x-rdc-dev-statuses/x-rdc-dev-transitions，contract 镜像+契约测试锁死，DDL 不加 CHECK。只有 DevService.Advance/Skip 写 status（仓储唯一写入点 UpdateStatusIf，WHERE status=from 防并发跳级）。
- 聚合双实现：Go 的 contract.AggregateDevStatus 展示 + SQL MIN(CASE)+COALESCE(min_ord,7) 筛选，测试对 9×9 组合钉死一致。
- team 专属表不进 FOREACH、单仓储固定 PartitionTeam；task_id ON DELETE CASCADE；requirement_id FK 不级联（需求无删除路径）。
- 5 占位块迁到详情抽屉纯文字（DevPlaceholderFeatures），推进按钮文案"推进状态到 X"不暗示真实执行；03/04 仍用未改的 RdcPlaceholderPage。

### QA 发现的真实 bug 与修复（重要教训）
- **并发推进时审计 from→to 跳级**：handler 用 devSubtaskContext 预读 from、service 又读一次，并发窗口下旧 from 配新 to → 审计出现状态机不存在的跃迁（状态机与落库本身正确，6 个陈旧请求都 400）。
- 修法：DevService.Advance/Skip 返回 (subtask, from, error)，from=同一次 findSubtask 快照的 subtask.Status；handler 删预读、直接用返回的 from；writeStatus 回读后把返回 DTO 的 Status 固定为本次写入的 to（防回读期间被并发推进的残留窗口）。新增回归 TestAdvanceAuditPairStaysAdjacentUnderConcurrentReread。
- **教训：审计字段若与业务操作分两次读同一可变状态，并发下必然漂移。审计的 from 必须与条件更新的 from 同源（同一次快照）。**
